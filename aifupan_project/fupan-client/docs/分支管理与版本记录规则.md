# 分支管理与版本记录规则

## 1. 概述

本文档定义项目的分支管理策略和版本变更记录规则，解决当前 `dev-xxx` / `test-xxx` / `reslease-xxx` 多分支并行开发时的变更追踪难题。

**核心设计原则：**
- **开发过程追踪**：`dev-X.Y.Z.W` 微分支的功能记录 → `docs/版本开发目录/X.Y.Z.md`
- **集成变更记录**：`test-X.Y.Z` 和 `reslease-X.Y.Z` 的变更 → `docs/版本变更/X.Y.Z.md`
- **自动合并摘要**：当 dev 分支合并到 test/reslease 时，AI 自动将开发记录摘要写入版本变更文件

---

## 2. 分支命名规范

### 2.1 完整格式

```
<类型前缀>-<主版本>.<次版本>.<修订号>.<功能序号>
```

| 前缀 | 用途 | 示例 |
|------|------|------|
| `dev-` | 功能开发分支（微分支） | `dev-2.6.2.1`、`dev-2.6.2.2` |
| `test-` | 测试集成分支 | `test-2.6.2` |
| `reslease-` | 预发布/候选分支 | `reslease-2.6.2` |

### 2.2 大版本提取规则

从分支名中提取大版本号（忽略前缀）：

- `dev-2.6.2.1` → 大版本 `2.6.2`，功能序号 `1`
- `dev-2.6.2.2` → 大版本 `2.6.2`，功能序号 `2`
- `test-2.6.2` → 大版本 `2.6.2`
- `reslease-2.6.2` → 大版本 `2.6.2`

**解析算法：**
```
1. 去除前缀（dev- / test- / reslease-）
2. 取前 3 段数字作为大版本（X.Y.Z）
3. 第 4 段数字作为功能序号（仅 dev 分支有）
```

### 2.3 开发流程

```
dev-2.6.2.1 ──┐
dev-2.6.2.2 ──┼──→ test-2.6.2 ──→ reslease-2.6.2 ──→ 发布
dev-2.6.2.3 ──┘
```

- 每个功能从对应的 test/reslease 分支切出 `dev-X.Y.Z.W` 开发
- 开发完成后合并到 `test-X.Y.Z`
- 测试通过后合并到 `reslease-X.Y.Z`
- `reslease-X.Y.Z` 用于最终发布

## 3. 文件结构

### 3.1 版本开发目录（新增）

```
docs/版本开发目录/
├── README.md           # 本目录说明
├── 2.6.2.md            # 大版本 2.6.2 的开发记录
├── 2.6.3.md            # 大版本 2.6.3 的开发记录
└── ...
```

**文件命名规则：** `<大版本号>.md`（如 `2.6.2.md`）

**文件内容格式：**

```markdown
# dev-2.6.2 大版本开发记录

---

## 2.6.2.1 分支
**功能名称**：巨量+来客授权统一选择组件

**变更时间**：2026-07-30

**变更文件**：

**功能描述**：
封装授权方式统一入口组件，支持弹窗/按钮两种模式。弹窗模式打开 radio 选择弹窗，自动调用云端 getAuthStatus 查询授权状态并置灰已授权平台；按钮模式内联渲染授权按钮+状态标签。内置 PLATFORM_CAPABILITIES 集中管理巨量/来客/千川等各平台授权动作。

**合并状态**：已合并至 test-2.6.2

## 2.6.2.2 分支
**功能名称**：商品数据 Tab 及空态逻辑

...（类似格式）
```

### 3.2 版本变更目录（已有，规则调整）

```
docs/版本变更/
├── README.md
├── 2.6.2.1.md
├── 2.6.2.2.md
├── 2.6.2.3.md
└── ...
```

**调整点：** 变更来源从 "dev-xxx 分支" 改为 "test-xxx 和 reslease-xxx 分支"

### 3.3 版本变更文件新增：「版本功能明细」

每个 `docs/版本变更/X.Y.Z.md` 文件在现有的「变更明细」表格之外，**新增一个「版本功能明细」章节**，用于测试团队作为测试清单。

**定位：** 位于文件末尾（在「变更明细」表格之后），用 `---` 分隔。

**内容规则：**
- **不记录"改了什么"**（那是变更明细表格的职责）
- **只记录"当前版本有哪些功能"**——以功能视角列出完整的功能清单和功能概述
- 每个功能一行，包含功能名称和功能概述
- 若功能在后续版本中被移除，从明细中删除或标记为 ~~已移除~~
- 若功能是继承自上一版本（未改动），也应在明细中列出（确保清单完整性）

**格式：**

```markdown
---

## 版本功能明细

> 以下为当前版本完整功能清单，供测试团队作为测试验收清单使用。

| 序号 | 功能名称 | 功能概述 | 涉及模块 |
| --- | --- | --- | --- |
| 1 | AI整场复盘列表 ASR 加速 | 在分析状态为待分析的场次中提供"加速分析"入口，点击后按钮切换为"正在加速中"并禁止重复点击 | replay |
| 2 | AI 智能体工作台首次引导弹窗 | 进入分析详情页时每日首次自动弹出引导弹窗，关闭或点击"立即体验"后记为当日已展示 | 分析详情 / AI智能体 |
| 3 | 商品数据 Tab | 详情页新增商品数据 Tab，支持商品分页拉取、列表展示、排序和关键字搜索 | analysis |
| 4 | ROI 数据企业版门禁 | 投放数据 Tab 仅企业版及以上可查看实际数据，非企业版点击后展示权限提示语句 | analysis |
| ... | ... | ... | ... |
```

**维护规则：**

| 场景 | 操作 |
|------|------|
| dev 分支合并到 test/reslease（新功能） | 在版本功能明细中**新增一行** |
| 功能从当前版本移除 | 将对应行标记为 `~~已移除~~` 或直接删除 |
| 功能更新/增强 | 更新对应行的「功能概述」 |
| 上一版本继承功能（未改动） | 保留在明细中，不做标记 |

**AI 自动维护时机：**
- 当 dev 分支合并到 test/reslease 时，自动从 `docs/版本开发目录/X.Y.Z.md` 读取功能描述，追加到版本功能明细
- 当在 test/reslease 分支直接修改功能时，同步更新版本功能明细中对应的概述

## 4. AI 行为规则

### 4.1 进入 dev-X.Y.Z.W 分支时

当 AI 检测到当前分支为 `dev-X.Y.Z.W` 格式时：

1. **检测大版本目录文件是否存在**
   - 检查 `docs/版本开发目录/X.Y.Z.md` 是否存在
   - 不存在 → 创建文件，写入基础结构（大版本标题）

2. **检测当前功能分支是否已记录**
   - 在 `docs/版本开发目录/X.Y.Z.md` 中搜索 `X.Y.Z.W 分支`
   - 不存在 → 追加空记录模板：
     ```markdown
     ## X.Y.Z.W 分支
     **功能名称**：待补充
     **变更时间**：<当前日期>
     **变更文件**：待补充
     **功能描述**：待补充
     **合并状态**：开发中
     ```

3. **每次在该分支提交代码时**
   - 更新 `docs/版本开发目录/X.Y.Z.md` 中当前功能分支的记录
   - 补充变更文件列表和功能描述
   - 写入 `docs/版本开发目录/X.Y.Z.md` 的更新

4. **重复分支变更检测（每次执行任务前）** ⚠️
   - **适用分支**：仅 `dev-X.Y.Z.W` 分支（`aiDev-*` 分支不检测）
   - **检测逻辑**：
     1. 读取当前大版本的开发记录 `docs/版本开发目录/X.Y.Z.md`
     2. 列出同大版本下**其他 dev- 微分支**已记录的变更文件列表
     3. 在执行当前任务前，将本次任务可能修改的文件与同大版本其他分支的变更文件做**交集比对**
     4. 若存在重叠文件（同一文件被 2 个及以上 dev 分支修改），则：
        - **暂停任务执行**
        - 向用户发出提醒，格式如下：
          ```
          ⚠️ 重复分支变更提醒
          当前分支：dev-X.Y.Z.W（功能名称）
          与以下分支存在文件冲突：
            - dev-X.Y.Z.X（功能名称）：冲突文件 xxx.vue
            - dev-X.Y.Z.Y（功能名称）：冲突文件 yyy.js
          建议：请确认是否需要先合并这些冲突分支，或当前功能是否应等待上述分支完成后再开发。
          请输入"继续"忽略提醒并继续执行，或输入"切换"切换到指定分支。
          ```
     5. 等待用户确认后继续执行
   - **豁免规则**：以下情况不检测
     - 当前分支为 `aiDev-*` 格式（Agent 自动派发任务）
     - 同大版本下仅有当前分支（无其他 dev 分支）
     - 用户已明确要求忽略（如说"跳过检测"）

### 4.2 进入 test-X.Y.Z 或 reslease-X.Y.Z 时

1. **变更记录来源**
   - 不再从 dev-xxx 分支提取变更
   - 直接从当前分支（test/reslease）的代码变更中提取

2. **提交时自动记录**
   - 提取当前 Git 分支名中的版本号（忽略 test/reslease 前缀）
   - 若本次提交包含 `src/` 等代码文件变更，将变更写入 `docs/版本变更/X.Y.Z.md`
   - 若版本号与分支不一致，阻止提交并清理本次对版本文档的修改

### 4.3 合并 dev → test/reslease 时

当检测到 `dev-X.Y.Z.W` 合并到 `test-X.Y.Z` 或 `reslease-X.Y.Z` 时：

1. **读取开发记录**
   - 读取 `docs/版本开发目录/X.Y.Z.md` 中 `X.Y.Z.W 分支` 的功能描述

2. **摘要写入版本变更明细表格**
   - 将功能摘要转换为版本变更表格行格式，写入 `docs/版本变更/X.Y.Z.md` 的「变更明细」表格

3. **同步写入版本功能明细**
   - 在 `docs/版本变更/X.Y.Z.md` 的「版本功能明细」表格中新增一行
   - 如果该功能是对已有功能的增强，更新对应行的「功能概述」
   - 保证版本功能明细始终反映当前版本完整的功能清单

4. **更新合并状态**
   - 在 `docs/版本开发目录/X.Y.Z.md` 中将 `合并状态` 更新为 `已合并至 test-X.Y.Z` 或 `已合并至 reslease-X.Y.Z`

### 4.4 当前在 aiDev-xxx 分支时（Agent 自动派发任务）

`aiDev-*` 分支由 Agent 自动派发，属于无人值守的自动化任务分支：
- **不做任何自动记录操作**（不写入版本开发目录）
- **不触发重复分支变更检测**
- **不触发版本变更文件更新**
- 任务完成后由 Agent 自行提交并合并

### 4.5 当前在其他非规范分支时

如果当前分支不属于 `dev-*` / `test-*` / `reslease-*` 格式：
- 不做任何自动记录操作
- 若用户要求记录，提示分支格式不匹配

## 5. Hook 修改方案

### 5.1 SessionStart Hook（`emit-bootstrap.js`）

**新增注入内容：**
- 当前分支类型识别（dev/test/reslease/aiDev/other）
- 若为 `aiDev-*`：
  - 标记为 Agent 自动任务模式
  - 跳过所有版本记录检查和重复分支检测
- 若为 `dev-X.Y.Z.W`：
  - 提示检查 `docs/版本开发目录/X.Y.Z.md` 是否存在
  - 若不存在则需创建
  - 提醒在当前分支提交时更新开发记录
  - **触发重复分支变更检测**（见 4.1.4）
- 若为 `test-X.Y.Z` 或 `reslease-X.Y.Z`：
  - 提醒代码变更需更新 `docs/版本变更/X.Y.Z.md`

### 5.2 PostToolUse Hook（`check-doc-maintenance.js`）

**新增检查逻辑：**

在原治理文件检查基础上，新增分支版本管理检查：

```javascript
/**
 * @description 检查是否需要在版本记录文件中记录。
 */
function checkVersionDocMaintenance(payload, branchInfo) {
  // 1. 获取当前分支信息
  const { prefix, majorVersion, featureIndex } = branchInfo

  // aiDev 分支跳过所有检查
  if (prefix === 'aiDev') return null

  // 2. 获取本次修改的文件
  const filePaths = collectFilePaths(payload)

  // 3. 如果修改了 src/ 下的代码文件
  if (hasSourceChanges(filePaths)) {
    if (prefix === 'dev' && featureIndex !== undefined) {
      // dev 分支 → 提醒更新 docs/版本开发目录/X.Y.Z.md
      return {
        file: `docs/版本开发目录/${majorVersion}.md`,
        section: `${majorVersion}.${featureIndex} 分支`,
      }
    }
    if (prefix === 'test' || prefix === 'reslease') {
      // test/reslease 分支 → 提醒更新 docs/版本变更/X.Y.Z.md
      return {
        file: `docs/版本变更/${majorVersion}.md`,
      }
    }
  }

  return null
}
```

**重复分支检测（独立 Hook 或内嵌逻辑）：**

```javascript
/**
 * @description dev-* 分支的重复变更检测（aiDev-* 分支不触发）。
 * @returns {{ conflict: boolean, conflicts: Array<{branch, files}> } | null}
 */
function checkDuplicateBranchChanges(branchInfo) {
  const { prefix, majorVersion, featureIndex } = branchInfo

  // 仅 dev-* 分支检测，aiDev-* 和 test/reslease 不检测
  if (prefix !== 'dev' || featureIndex === undefined) return null
  // aiDev 前缀的 dev 分支不检测（虽然是 dev- 前缀）
  // 注：实际实现中通过分支名前缀 aiDev 判断

  // 1. 读取 docs/版本开发目录/X.Y.Z.md
  // 2. 解析出其他 dev- 分支的变更文件列表
  // 3. 与当前修改文件做交集
  // 4. 如有冲突 → 返回冲突信息
  // 5. 无冲突 → 返回 null
}
```

### 5.4 `.trae/rules/project_rules.md` 调整

更新"版本变更记录规则"部分，修改为：

## 6. AI 执行清单（CheckList）

每次 AI 启动或在分支间切换时执行：

### 6.1 分支检测
- [ ] 执行 `git branch --show-current` 获取当前分支名
- [ ] 解析分支前缀（dev/test/reslease/aiDev）
- [ ] 若为 `aiDev-*` → 标记为 Agent 自动任务，跳过后续所有检查
- [ ] 解析大版本号（X.Y.Z）和功能序号（W）

### 6.2 dev 分支初始化
- [ ] 检查 `docs/版本开发目录/X.Y.Z.md` 是否存在
- [ ] 不存在 → 创建文件，填入标题 `# dev-X.Y.Z 大版本开发记录`
- [ ] 检查当前功能分支 `X.Y.Z.W 分支` 是否已记录
- [ ] 未记录 → 追加空记录模板，标记 `**合并状态**：开发中`

### 6.3 重复分支冲突检测（仅 dev-* 分支）
- [ ] 读取 `docs/版本开发目录/X.Y.Z.md` 中**其他 dev- 分支**的变更文件列表
- [ ] 将本次任务预期修改的文件与其他分支变更文件做**交集比对**
- [ ] 无冲突 → 继续执行
- [ ] 有冲突 → 暂停并提醒用户，等待用户确认（继续/切换分支）

### 6.4 代码提交时
- [ ] **dev 分支**：更新 `docs/版本开发目录/X.Y.Z.md` 中当前分支的记录
- [ ] **test/reslease 分支**：更新 `docs/版本变更/X.Y.Z.md`

### 6.5 合并时
- [ ] 识别 merge commit 的来源分支和目标分支
- [ ] 若来源为 `dev-X.Y.Z.W`、目标为 `test-X.Y.Z`：
  - [ ] 读取 `docs/版本开发目录/X.Y.Z.md` 中对应功能描述
  - [ ] 摘要写入 `docs/版本变更/X.Y.Z.md` 的「变更明细」表格
  - [ ] 同步写入/更新「版本功能明细」表格（新增或更新对应功能行）
  - [ ] 更新 `docs/版本开发目录/X.Y.Z.md` 中的合并状态

## 7. 示例场景

```

3. AI 检查 docs/版本开发目录/ 是否存在 2.6.3.md

     # dev-2.6.3 大版本开发记录

4. 用户在 dev-2.6.3.1 上开发、提交

6. 开发完成，合并到 test-2.6.3
7. AI 检测到合并操作：
   - 读取 2.6.3.md 中 2.6.3.1 的功能描述
   - 摘要写入 docs/版本变更/2.6.3.md
   - 更新 2.6.3.md 中 2.6.3.1 的合并状态为 "已合并至 test-2.6.3"
```
