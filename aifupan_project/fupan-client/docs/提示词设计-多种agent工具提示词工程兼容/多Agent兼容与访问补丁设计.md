# 多 Agent 兼容与访问补丁设计

## 1. 背景与问题定义

当前很多 Agent 工具虽然都支持“项目级规则文件”，但它们读取规则的方式并不一致：

- 有的工具倾向于读取固定命名文件，如 `CLAUDE.md`
- 有的工具会同时读取多个层级的入口文件，例如仓库根 `CLAUDE.md` 与 `.claude/CLAUDE.md`
- 有的工具倾向于读取规则目录，如 `.claude/rules/`、`.trae/rules/`
- 有的工具只会看到一个入口文件，却不会自动继续读取入口文件中引用的提示词工程目录

这会导致一个典型问题：

> Agent 看到了“映射关系”，却没有真正进入提示词工程的单一来源目录继续读取。

于是就出现以下风险：

- 只看到了入口桥，看不到完整治理规则
- 只看到一句摘要，看不到触发条件与门禁
- 只知道有 `wiki/skills/memory`，却没有沿索引继续查询
- 多个 Agent 各自补一套文件，最终造成多套提示词工程并存

## 2. 设计目标

本补丁的目标不是再造一套提示词工程，而是给已有提示词工程增加一层“多 Agent 访问兼容层”：

### 2.1 统一单一来源

- 提示词工程只有一份长期维护的主目录
- 本项目采用：`agnet/`
- 任何 Agent 工具都只能桥接到这份单一来源，而不能自己维护一套独立业务规则

### 2.2 统一访问入口

- 对不同 Agent 提供各自工具约定的入口文件名
- 入口文件允许内联少量关键规则，但不承载完整业务知识
- 所有入口最终都必须回到 `agnet/BOOTSTRAP.md`

### 2.3 基础规则自动加载

- 基础治理规则必须自动进入上下文
- 不能完全依赖模型“看到路径后自觉去读”
- 优先用工具自带机制完成：
  - 入口文件
  - 规则目录
  - hooks

### 2.4 深层知识按需加载

- 基础规则自动加载
- wiki / skills / 领域知识按索引继续查询
- 避免把所有知识都塞进单个大入口文件，导致上下文膨胀

## 3. 核心设计：四层结构

### 3.1 第一层：单一来源层

职责：

- 保存真实的治理规则、技能、索引、知识图谱、长期记忆
- 作为所有 Agent 的最终事实来源

本项目对应目录：

- `agnet/`

建议包含：

- `AGENT.md`
- `TOOLS.md`
- `INDEX.md`
- `MEMORY.md`
- `POLICIES.md`
- `CHANGE_LOG.md`
- `wiki/`
- `skills/`
- `self_skills/`

### 3.2 第二层：统一引导层

职责：

- 为所有 Agent 提供统一的“首跳入口”
- 定义读取顺序、任务场景到文件链路、写回原则、多 Agent 兼容约束

本项目新增文件：

- `agnet/BOOTSTRAP.md`

设计原则：

- 它不是所有规则的副本
- 它是“如何进入真实规则体系”的导航入口
- 它必须足够短、足够强、足够明确

### 3.3 第三层：Agent 桥接层

职责：

- 适配具体工具的发现方式
- 将工具的默认加载行为桥接回单一来源

示例：

- Claude Code：`CLAUDE.md`
- Trae：`.trae/rules/*`
- 其他工具：各自固定入口文件

桥接层只允许做四类事：

- 映射
- 引导
- 自动加载
- 基础规则重注入

桥接层不允许做两类事：

- 长期维护独立业务事实
- 在桥接目录中持续堆积与单一来源脱节的知识副本

### 3.4 第四层：确定性自动化层

职责：

- 把“模型可能忘”的事情变成“每次都会执行”
- 例如在会话开始、恢复、压缩后重新注入基础治理上下文

典型手段：

- hooks
- 项目级 settings
- 自动体检 / 自动注入脚本

## 4. 为什么不能只靠入口文件

只靠入口文件会遇到三个问题：

### 4.1 入口文件是声明，不是强制执行链

如果入口文件只写：

- `→ agnet/AGENT.md`
- `→ agnet/CHANGE_LOG.md`

那么模型看到的是“路径映射”，不是“必须继续读取”的执行链。

### 4.2 单个入口文件信息密度有限

如果把所有规则都塞进入口文件：

- 文件会越来越长
- 模型遵循率反而下降
- 一些深层知识会淹没高优先级规则

### 4.3 规则摘要不等于规则触发条件

例如只写：

- 新知识先写 wal/

这并没有回答：

- 什么算“新知识”
- 什么情况下必须写 CHANGE_LOG
- 什么内容不能进 WAL
- 何时必须继续读 skills/wiki

因此必须把入口文件和规则目录、hooks 组合起来使用。

## 5. 推荐补丁模式

### 5.1 模式 A：入口桥

给目标 Agent 增加入口桥文件，并在入口中内联少量关键规则：

- 说明 `agnet/` 是单一来源
- 直接内联高优先级治理规则，而不是只给路径映射
- 说明读取本文件后必须继续读取 `agnet/BOOTSTRAP.md`
- 明确如果桥接层与单一来源冲突，以单一来源为准

适合：

- 只支持固定命名入口文件的工具

### 5.2 模式 B：规则分片

把“始终生效”的高优先级规则拆成多份小规则文件，让工具在启动时自动加载。

建议分片为：

- 核心治理
- 上下文漏斗
- 写回与变更记录
- 多 Agent 兼容边界

适合：

- 支持规则目录自动加载的工具

### 5.3 模式 C：SessionStart 重注入

利用 hooks 在以下场景重新注入一段简短、稳定的基础上下文：

- 启动
- 恢复
- `/clear`
- `/compact`

适合：

- 支持项目级 hooks 的工具

价值：

- 防止压缩上下文后把基础治理规则丢掉
- 防止多轮会话后只剩业务上下文，忘记治理规则

### 5.4 模式 D：PostToolUse 文档维护检查

利用 `PostToolUse` 在文件修改成功后触发自动检查：

- 判断本次是否修改了规则、桥接层、hooks、兼容文档
- 若命中治理文件，则向 Claude 注入“检查 CHANGE_LOG / POLICIES / 兼容文档”的提醒
- 把“文档维护检查”从纯自觉行为升级为工具执行后的自动补强

## 6. 本项目采用的落地结构

### 6.1 单一来源

- `agnet/`

### 6.2 统一引导层

- `agnet/BOOTSTRAP.md`

### 6.3 Claude Code 桥接层

- `CLAUDE.md`
- `.claude/CLAUDE.md`
- `.claude/rules/00-core-governance.md`
- `.claude/rules/10-context-funnel.md`

## 7. 为什么 hooks 值得引入

根据 Claude Code 官方能力：

- 项目级 `.claude/settings.json` 支持 `hooks`
- Claude Code 会读取仓库根 `CLAUDE.md` 与 `.claude/CLAUDE.md`，并做合并加载
- `SessionStart` 可在启动、恢复、清理、压缩时触发
- `PostToolUse` 可在工具写文件成功后触发
- hooks 可以通过 `additionalContext` 向 Claude 注入额外上下文
- `.claude/rules/` 可作为规则目录被 Claude Code 加载
- `CLAUDE.md` 支持导入额外文件，且官方明确建议当仓库已有 `AGENTS.md` 等其他 Agent 文件时，可创建 `CLAUDE.md` 进行桥接导入

这意味着：

- 根目录入口负责“简短摘要 + 关键规则内联”
- `.claude/CLAUDE.md` 负责“详细配置 + 强制继续读取”
- 规则分片负责“自动常驻”
- SessionStart 负责“重注入与兜底”
- PostToolUse 负责“文档维护检查”

五者组合后，Claude Code 就不会只停留在“看到一个映射表”这一步了。

## 8. 对其他 Agent 的通用迁移方式

迁移到其他 Agent 时，不需要复制整个桥接层，只需要遵循下面的通用规则：

### 8.1 保持单一来源不变

- 沿用 `.agent/`、`agent/` 或 `agnet/` 其中一种
- 只保留一套真实治理资产

### 8.2 为目标 Agent 做轻桥接

- 创建目标 Agent 需要的入口文件
- 如果工具支持双入口，再创建一份“工具目录详细配置入口”
- 明确指向统一 `BOOTSTRAP.md`
- 明确桥接层不是单一来源

### 8.3 能用规则目录就用规则目录

- 将高优先级规则拆成多份短文件
- 用工具原生规则发现机制自动加载

### 8.4 能用 hooks 就加 hooks

- 至少在 SessionStart 注入一次基础治理摘要
- 如工具支持，再补一个 PostToolUse 文档维护检查
- 如工具支持，还可在压缩、恢复、停止等时机继续补强

## 9. 管理原则

### 9.1 单一来源只维护一份

- 规则在 `agnet/`
- 知识在 `agnet/wiki/`
- 技能在 `agnet/skills/` 与 `agnet/self_skills/`

### 9.2 桥接层尽量薄

桥接层不做：

- 大量业务事实堆积
- 大段知识副本
- 单独维护一套长期记忆

桥接层只做：

- 自动加载
- 指向单一来源
- 强制继续读取
- 重注入基础规则

### 9.3 治理变更必须可追溯

只要涉及：

- 入口桥
- 规则目录
- hooks
- 多 Agent 兼容边界

都应该写入 `CHANGE_LOG.md`，并在必要时沉淀为 `POLICIES.md`。

## 10. 结论

多 Agent 共仓的关键，不是给每个 Agent 都配一份完整提示词工程，而是：

1. 保持只有一套真实单一来源
2. 提供统一的 `BOOTSTRAP` 导航入口
3. 用各工具自己的入口机制做轻桥接，并在入口中内联少量关键规则
4. 用规则目录、SessionStart 与 PostToolUse 把基础规则自动加载和文档维护检查做成确定性行为

这样才能同时满足：

- 统一管理
- 统一记忆
- 统一知识
- 统一技能
- 多工具兼容
- 低维护成本

## 11. 通用化：把 Claude 方案抽象成“跨工具适配器补丁”

本项目在 Claude Code 上验证的关键不是“某个文件名”，而是一套可迁移的方法：

1. 单一来源（Canonical）只维护一份：规则、记忆、wiki、skills 全部回到单一来源目录。
2. 统一入口（BOOTSTRAP）作为“读取导航器”：明确必读顺序、任务场景链路、写回规则。
3. 入口桥（Entry Bridge）必须内联少量关键规则：避免只剩路径映射导致规则不生效。
4. 规则目录（Rules Dir）承载始终生效约束（若工具支持）：把“硬规则”自动注入上下文。
5. hooks 兜底（若工具支持）：
   - SessionStart：启动/恢复/压缩后重注入基础治理摘要
   - PostToolUse：写文件成功后触发文档维护检查提醒

将上述五点抽象后，每个工具只需要做一件事：

> 先自检“我会自动读取哪些入口/目录/是否支持 hooks”，再按同一套分层方案实现自己的适配器，把默认加载链路桥接回 BOOTSTRAP。

### 11.1 补丁包位置

本仓库提供可复制的通用补丁包模板：

- `docs/提示词设计-多种agent工具提示词工程兼容/patch/`
  - `agent-bridge.manifest.sample.json`：桥接清单示例（机器可读）
  - `adapter-checklist.md`：适配器实现与验收清单
  - `README.md`：补丁包使用方式

本仓库已提供一个可复用 skill：

- `/.trae/skills/multi_agent_prompt_bridge/SKILL.md`

用途：

- 当你把补丁包复制到新项目后，让目标 Agent 自己输出“入口读取规则自检表”，再按 checklist 落地适配器文件与 hooks。
