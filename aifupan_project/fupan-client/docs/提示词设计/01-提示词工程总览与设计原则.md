# 提示词工程总览与设计原则

## 1. 本工程在解决什么问题

传统提示词往往只有一段系统提示或几份零散说明，容易出现以下问题：

- 规则散落在不同工具或聊天上下文里，无法追溯。
- 对话一长，智能体会被无关上下文污染，开始偏离目标。
- 同一类任务没有稳定做法，输出质量波动大。
- 新经验难以沉淀成团队资产，只能重复沟通。
- 一旦多人协作，知识库、技能说明、规则文档会快速膨胀并相互冲突。

`fupan-client` 的 `agent/` 目录针对这些问题，已经构建出一套“工程化提示词体系”。它的本质不是一堆 prompt 文案，而是一套围绕“可执行、可沉淀、可治理、可升级”设计的工作系统。

## 2. 设计目标

从当前项目抽取后，可以归纳出 6 个核心目标：

### 2.1 可交付

- 智能体不只负责“回答”，而是负责推动页面、组件、状态、接口、验收等工程结果落地。
- 所有提示词规则都围绕可交付物展开，而不是围绕泛化聊天能力展开。

### 2.2 可追溯

- 关键规则、结论、技能、知识节点都要落在仓库文件内。
- 后续任何人都可以从文件系统反查：为什么有这个规则、入口在哪、什么时候改的。

### 2.3 可复用

- 重复动作要抽象成技能。
- 高频知识要抽象成 wiki 页面或 MEMORY 摘要。
- 协作流程要抽象成模板和门禁，而不是靠个人习惯。

### 2.4 可治理

- 不允许无节制地向总文档堆内容。
- 不允许新技能创建后无人可发现。
- 不允许把敏感信息、临时状态、一次性细节直接写入长期资产。

### 2.5 可升级

- 工程本身支持版本号、补丁包、同步脚本、CHANGE_LOG 留痕。
- 提示词工程要能独立迭代，而不是每次都整包重建。

### 2.6 可迁移

- 将业务绑定内容与通用方法论分开。
- 通用层可复制到其他项目，项目层只保留当前仓库特有路径、组件、业务约定。

## 3. 核心设计原则

## 3.1 单一来源

当前项目将 `agent/` 作为单一来源目录，规则层再映射到 `.trae/rules/` 等平台发现目录。这样做的价值是：

- 真正需要维护的源头只有一个。
- 不会因为 IDE、Agent 平台、其他工具各自持有一份规则副本而漂移。
- 迁移到其他工具时，只需要新增同步层，不需要重写工程。

## 3.2 规则与知识分层

本项目把不同类型的信息强制拆层：

| 层 | 作用 | 典型文件 |
| --- | --- | --- |
| 角色规则层 | 定义身份、职责、交付物、硬约束 | `AGENT.md` |
| 导航图谱层 | 定义概念节点、关系与入口 | `INDEX.md`、`wiki/KNOWLEDGE_GRAPH.md` |
| 内容知识层 | 沉淀细节、范式、案例 | `wiki/**` |
| 长期记忆层 | 保留高频稳定摘要 | `MEMORY.md` |
| 技能执行层 | 固化可复用操作单元 | `skills/**`、`self_skills/**` |
| 治理与演化层 | 留痕、反思、策略、版本升级 | `POLICIES.md`、`DREAMS.md`、`CHANGE_LOG.md`、`versions/**` |

这是一种非常重要的可复用经验：不要把所有内容堆进一个总 prompt 或一个总 wiki。

## 3.3 最小上下文加载

提示词工程不是“信息越多越好”，而是“加载刚刚够用的信息”。因此项目采用“上下文漏斗”：

1. 先从总索引和知识图谱入口进入。
2. 再选择任务对应的知识域。
3. 只有当域索引不足以支撑决策时，才继续读具体页面或代码。

好处是：

- 降低上下文长度和成本。
- 降低误读无关文档的概率。
- 降低多人协作时的认知冲突。

## 3.4 增量写回而非直接改总文档

项目没有让所有知识直接写进 `index.md` 或 `MEMORY.md`，而是采用：

`WAL -> index/wiki -> MEMORY`

其含义是：

- 新知识先以 WAL 片段形式追加。
- 之后按窗口合并到域索引或内容页。
- 最后只有高频稳定结论才升格到长期记忆。

这套机制非常适合多人协作与长期迭代项目。

## 3.5 技能优先而非临时发挥

项目明确规定：

- 先查 `self_skills/`
- 再查 `skills/`
- 缺失时才新建技能

这是一个非常关键的设计。它将“个人经验”转化成“可重复调用的能力单元”，防止每次都从零发挥。

## 3.6 结构性变更必须留痕

不是只有业务代码改动需要记录，提示词工程的这些变化也必须记录：

- 规则变更
- 技能结构变更
- 索引结构变更
- 安全边界变更
- 治理流程变更

因此引入 `CHANGE_LOG.md` 作为治理变更日志，而不是只依赖 Git diff。

## 4. 抽取出的总体架构

将 `agent/` 抽象后，可以形成下面这张通用架构图：

```text
用户请求
  ↓
角色规则层（身份/边界/硬约束）
  ↓
意图路由层（Learn / Patch / Standard / Governance）
  ↓
上下文漏斗（INDEX -> KNOWLEDGE_GRAPH -> 域 index -> 细节页）
  ↓
技能执行层（self_skills 优先，skills 次之）
  ↓
实现或分析产物
  ↓
验证与门禁
  ↓
写回链路（WAL -> wiki/index -> MEMORY -> CHANGE_LOG）
  ↓
长期可复用资产
```

## 5. Prompt Pack 的模块化设计

虽然当前项目没有单独命名为 “Prompt Pack”，但从整体结构看，已经隐式拆成了多个可复用模块：

### 5.1 P0 角色与硬规则

来源：

- `AGENT.md`
- `.trae/rules/frontend_agent__AGENT.md`
- `.trae/rules/project_rules.md`
- `.trae/rules/teammate_rules.md`

解决的问题：

- 你是谁
- 你要交付什么
- 什么不能做
- 你的规则优先级是什么

### 5.2 P1 上下文漏斗

来源：

- `wiki/KNOWLEDGE_GRAPH.md`
- `wiki/通用-上下文漏斗与写回.md`

解决的问题：

- 先读什么
- 哪些内容默认不读
- 什么时候才下沉到更细页面

### 5.3 P2 范围控制

来源：

- `templates/focus_card.md`

解决的问题：

- 目标是什么
- 做什么、不做什么
- 能改哪些路径
- 如何验收、如何回滚

### 5.4 P3 生命周期与门禁

来源：

- `wiki/通用-生命周期与门禁.md`
- `wiki/通用-意图路由与执行档位.md`

解决的问题：

- 不同任务应该用什么执行档位
- 每个阶段应该产出什么
- 哪些情况必须阻塞推进

### 5.5 P4 写回规则

来源：

- `wiki/通用-上下文漏斗与写回.md`
- `wiki/通用-WAL与防膨胀规则.md`
- `templates/wal_*.md`

解决的问题：

- 新知识写到哪里
- 怎么避免文档膨胀
- 什么时候可以进入长期记忆

### 5.6 P5 自我升级与治理

来源：

- `MEMORY.md`
- `POLICIES.md`
- `DREAMS.md`
- `CHANGE_LOG.md`
- `versions/**`

解决的问题：

- 什么该记住
- 什么该反思
- 什么该作为结构变更留痕
- 工程如何持续升级

## 6. 生命周期设计

从当前项目可以提炼出一套非常清晰的通用生命周期：

1. `Clarify`
2. `Explore`
3. `Propose`
4. `Implement`
5. `Verify`
6. `Writeback`

每一步的通用含义如下：

| 阶段 | 核心动作 | 典型产物 |
| --- | --- | --- |
| Clarify | 澄清目标、范围、非范围、风险 | Focus Card |
| Explore | 最小必要信息读取与定位 | 域入口、技能入口、关键代码/知识清单 |
| Propose | 给出方案、任务拆解、可回滚路径 | 任务计划、清单、验收点 |
| Implement | 实现或编写说明，保持增量修改 | 代码、文档、技能、wiki 产物 |
| Verify | 做基础诊断、自检、交叉核对 | 诊断结果、测试结果、自检说明 |
| Writeback | 沉淀知识和治理信息 | WAL、wiki、MEMORY、CHANGE_LOG |

## 7. 四类核心门禁

当前项目中最值得复用的是以下门禁设计：

### 7.1 Ambiguity Gate

- 需求不清楚、契约不明确、关键字段不确定时，禁止臆造。
- 正确做法是输出待确认项，而不是继续假设。

### 7.2 Scope Guard

- 超出 Focus Card 的允许触达路径时，禁止扩散改动。
- 这是防止智能体“顺手重构一大片”的关键机制。

### 7.3 Secrets Guard

- Token、密钥、个人隐私等敏感信息不得进入文档、WAL、记忆文件。
- 对私有化团队尤其重要。

### 7.4 Writeback Gate

- 只有高价值、稳定、可审计内容才允许写回长期资产。
- 结构/规则变更必须进入 `CHANGE_LOG.md`。

## 8. 从本项目抽取出的通用结论

- 提示词工程最佳形态不是“一个神奇大 Prompt”，而是“角色规则 + 图谱导航 + 知识域 + 技能层 + 治理层”的组合系统。
- 真正可复用的不是具体业务话术，而是这套分层、门禁、写回、技能化、留痕化的方法。
- 如果一个项目需要长期让多个智能体、多人开发者共同维护，这类工程化设计几乎是必需品，而不是锦上添花。
