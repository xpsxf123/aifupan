# 新项目落地与迁移手册

## 1. 本手册解决的问题

前面几份文档已经解释了这套提示词工程“是什么”和“为什么这样设计”。本文专门回答“如何在新项目中真正落地”。

适用场景：

- 新项目从零搭建提示词工程
- 老项目补建知识图谱和技能体系
- 团队准备把已有项目经验沉淀成可持续维护资产

## 2. 落地原则

迁移时不要追求一次复制全部能力，而应遵循以下原则：

### 2.1 先骨架，后内容

优先把目录、入口、规则和写回方式建立起来，再慢慢填充业务知识。

### 2.2 先通用，后项目

先迁移治理与通用技能，再逐步建立项目专属 `self_skills/`。

### 2.3 先可维护，后自动化

先让结构正确，再接 linter、compactor、schema 驱动等自动化能力。

### 2.4 先约束，后扩展

先明确哪些内容该写到哪里，避免一开始就失控膨胀。

## 3. 推荐的四阶段迁移方案

## 3.1 第一阶段：建立最小骨架

至少创建以下文件和目录：

```text
agent/
  AGENT.md
  INDEX.md
  MEMORY.md
  TOOLS.md
  CHANGE_LOG.md

  templates/
    focus_card.md
    wal_api_append.md
    wal_router_append.md
    wal_state_append.md
    wal_component_append.md

  wiki/
    README.md
    KNOWLEDGE_GRAPH.md
    api/index.md
    router/index.md
    state/index.md
    components/index.md
    preferences/index.md
    specs/index.md

  skills/
    INDEX.md
```

目标：

- 先把路由入口、知识域入口和治理文件搭起来。
- 即使内容为空，也先定义容器与规则。

## 3.2 第二阶段：迁移通用治理能力

优先迁移：

- 上下文漏斗规则
- WAL 规则
- 生命周期与门禁
- 技能治理规则
- 长期记忆压缩规则

建议做法：

- 将这些规则文档放进 `wiki/` 和顶层治理文件。
- 不要先复制一堆项目技能。

## 3.3 第三阶段：补通用技能

推荐先上这几类技能：

- 分析类：页面结构、接口依赖、状态共享
- 生成类：页面骨架、路由、API client
- 治理类：图谱构建、记忆压缩、技能索引治理

目标：

- 让工程具备“能分析、能生成、能沉淀”的基本闭环。

## 3.4 第四阶段：建设项目技能

在通用层稳定后，再针对项目建立 `self_skills/`：

- 列表页骨架
- 组件选型索引
- 弹窗/抽屉范式
- AI 内容渲染方式
- 项目特有布局与容器配方

目标：

- 将本项目的真实高频模式沉淀下来，而不是复制通用技能做重复劳动。

## 4. 新项目的初始化顺序

建议严格按这个顺序执行：

1. 写 `AGENT.md`
2. 写 `TOOLS.md`
3. 写 `INDEX.md`
4. 建 `wiki/KNOWLEDGE_GRAPH.md`
5. 建默认知识域
6. 建 `MEMORY.md`
7. 建 `templates/`
8. 建 `skills/INDEX.md`
9. 迁移 3~5 个最常用通用技能
10. 根据项目再建立 `self_skills/`

## 5. 每个核心文件应该如何初始化

## 5.1 `AGENT.md`

最少应包含：

- 角色身份
- 主要职责
- 默认交付物
- 三条硬规则
- 上下文获取原则
- 写回原则

### 建议不要一开始写太多

- 不要把项目所有细节放进 `AGENT.md`
- 不要把所有技能入口都堆进去
- 保持它是“角色宪法”，而不是百科文档

## 5.2 `INDEX.md`

初始化时建议只写：

- 核心路径
- 关键概念节点
- 少量关键关系

先让它能导航，不要追求一步到位。

## 5.3 `MEMORY.md`

初始化时建议只预留结构：

- 用户偏好
- 项目约束
- 高频结论

第一次迁移不要把旧聊天记录直接塞进去，应由治理过程逐步沉淀。

## 5.4 `TOOLS.md`

至少写清：

- skill 的目录约定
- 通用技能和项目技能的边界
- 技能使用优先级
- 新技能何时允许创建

## 5.5 `wiki/README.md`

建议说明：

- wiki 是内容层
- 页面怎么拆
- 推荐域有哪些
- 入口应从哪里进入

## 6. 知识域的推荐默认集合

对于绝大多数前端或全栈项目，建议默认建立 6 个域：

- `api`
- `router`
- `state`
- `components`
- `preferences`
- `specs`

如果项目比较复杂，再追加：

- `data`
- `security`
- `release`
- `testing`
- `observability`

## 7. 新项目的首批技能建议

如果你不想一开始迁太多，推荐首批只保留下面这些思路：

### 7.1 必选治理技能

- 图谱构建器
- 记忆压缩器
- 技能图谱治理器

### 7.2 必选分析技能

- 页面结构分析
- API 依赖分析
- 状态共享分析

### 7.3 可选生成技能

- 路由生成
- 页面骨架生成
- API client 生成
- mock 生成

## 8. 项目技能的建设方法

`self_skills/` 不要提前设计太多，建议通过真实项目问题反向沉淀：

### 适合沉淀为项目技能的信号

- 某种页面形态重复出现
- 某个组件族使用方式固定
- 某条业务流程总要解释多遍
- 某个兼容逻辑容易踩坑
- 某个布局或容器模式长期存在

### 不适合立刻沉淀的信号

- 刚出现一次
- 实现还在频繁变化
- 还没有稳定命名和路径

## 9. 写回机制如何接入日常工作

推荐把“写回”变成交付流程的一部分，而不是额外负担。

### 日常流程建议

1. 完成实现或分析
2. 提炼本次新增知识
3. 追加到对应域 WAL
4. 如有稳定结论，再更新 MEMORY
5. 如有结构变化，再更新 CHANGE_LOG

### 管理建议

- 不要求每次都写长文
- 只要求写“高价值、可复用、可审计”的信息
- 一旦写回习惯形成，后续维护成本会显著下降

## 10. 如何避免迁移失败

迁移最常见的失败方式不是“能力不够”，而是“顺序错误”。下面是几个典型坑位。

### 10.1 一开始复制太多项目技能

问题：

- 新项目没有对应组件和目录
- 技能大量失效

正确做法：

- 先迁通用层，再补项目层

### 10.2 把 INDEX 写成大而全说明书

问题：

- 索引失去导航作用
- 智能体最小加载被破坏

正确做法：

- 索引只保留摘要、链接、关系

### 10.3 把 MEMORY 当成总笔记

问题：

- 记忆污染
- 后续任务上下文被错误放大

正确做法：

- 只让高频稳定结论进入长期记忆

### 10.4 缺少技能索引

问题：

- 技能存在但找不到
- 团队继续重复造轮子

正确做法：

- 每新增技能必登记到 `INDEX.md`

### 10.5 没有写回门禁

问题：

- 文档快速膨胀
- 杂讯进入长期资产

正确做法：

- 用 WAL、MEMORY、CHANGE_LOG 分层控制

## 11. 自动化接入建议

当新项目运行稳定后，建议逐步接入自动化：

### 11.1 文档体检

检查：

- 死链
- 超长文档
- 孤岛页面

### 11.2 WAL 合并

检查：

- 待合并片段
- 合并后长度阈值
- 已应用片段归档

### 11.3 一致性校验

检查：

- 目录结构是否与规则一致
- 脚本路径是否与真实目录一致
- skills 是否都已登记索引

## 12. 团队协作建议

如果是多人团队，建议额外建立以下约束：

- 规则改动由少数治理责任人审核
- 项目技能必须附真实路径或示例
- 通用技能要尽量参数化
- 写回时强制避免敏感信息
- 每个迭代至少安排一次 WAL 合并与知识整理

## 13. 建议的验收标准

一个项目的提示词工程是否算落地成功，可以看以下 8 条：

1. 是否有单一来源目录
2. 是否有总索引与图谱入口
3. 是否有至少 4 个知识域
4. 是否有 WAL 写回机制
5. 是否有长期记忆文件
6. 是否有通用技能索引
7. 是否有项目技能或配方层
8. 是否有 CHANGE_LOG 或等效治理留痕

满足其中 6 条以上，基本就算已经进入工程化阶段。

## 14. 推荐的迁移结果形态

理想状态下，新项目最终应形成：

- 一个稳定的 `agent/` 根目录
- 一套薄索引、厚内容的知识体系
- 一组高频治理技能
- 一批按项目沉淀的 `self_skills/`
- 一条从任务交付到知识写回的闭环

这时提示词工程才真正成为“项目基础设施”，而不是“辅助说明”。
