# fupan-client现状提取与可复用清单

## 1. 本文目的

前面几份文档主要讲“抽象后的可复用方法”。本文专门回答两个现实问题：

- 当前 `fupan-client` 的 `agent/` 到底已经设计了什么。
- 这些设计里，哪些可以直接抽成通用工程能力，哪些只适合保留在本项目。

## 2. 当前项目提示词工程的总体成熟度判断

从当前目录和内容来看，这套工程已经具备以下成熟特征：

- 有明确的角色定义和硬规则。
- 有图谱式总入口和域化知识组织。
- 有长期记忆、策略、反思、变更日志四类治理文件。
- 有通用技能和项目技能分层。
- 有模板和治理脚本。
- 有版本升级目录，具备补丁式演进意识。

这说明当前项目不是“临时加了点提示词”，而是已经形成了一套可迁移的工程基础。

## 3. 当前项目里最值得抽取的通用设计

## 3.1 `agent/` 作为单一来源

价值：

- 平台无关
- Git 可管理
- 适合多工具复用

是否可复用：`是，强烈建议保留`

## 3.2 双层技能体系

价值：

- 通用技能负责方法论
- 项目技能负责本仓库配方

是否可复用：`是，强烈建议保留`

## 3.3 图谱 + 域索引 + WAL 的知识治理结构

价值：

- 支持最小上下文加载
- 支持多人协作写回
- 支持后续压缩与脚本治理

是否可复用：`是，强烈建议保留`

## 3.4 Focus Card 与生命周期门禁

价值：

- 防止范围漂移
- 让执行步骤可验收
- 让大型任务更可控

是否可复用：`是，强烈建议保留`

## 3.5 提示词工程版本化

价值：

- 支持补丁升级
- 支持分版本追溯

是否可复用：`建议保留，尤其适合私有化团队`

## 5. 当前项目中偏项目绑定的能力

以下内容虽然设计思路可复用，但实现本身强依赖 `fupan-client`：

### 5.1 `project_component_catalog`

原因：

- 直接依赖当前项目组件资源清单
- 直接依赖当前仓库目录与组件路径

可复用方式：

- 保留“组件资源索引与选型”这个思路
- 但具体内容必须替换为新项目自己的组件清单

### 5.2 `core_table_page_builder`

原因：

- 强依赖 `CoreTable` 组件
- 强依赖当前项目表格页约定

可复用方式：

- 可抽象为“标准列表页骨架生成器”
- 但在新项目里需要绑定新表格组件

### 5.3 `table_column_render_recipe`

原因：

- 强依赖当前项目列渲染实现方式

可复用方式：

- 可以复用“简单格式化 / 复杂 HTML / slot 插槽”三分法
- 但具体 API 需按项目组件改写

### 5.4 `dialog_drawer_recipe`

原因：

- 强依赖当前项目的 `dialog`、`drawer` 组件和 mixin 组织

可复用方式：

- 可以复用“受控弹窗规范”这套思想
- 但路径、参数、事件名需重建

### 5.5 `ai_content_rendering_pipeline`

原因：

- 强依赖当前项目 AI 渲染入口和兼容路径

可复用方式：

- 适合迁移到其他 AI 内容渲染类项目
- 但必须替换为新项目自己的渲染组件与格式约定

## 6. 可复用度分层建议

为了方便后续迁移，建议把当前项目资产按 3 个等级分类。

| 级别 | 说明 | 处理建议 |
| --- | --- | --- |
| A 级 | 可直接复用 | 原样复制，少量改名即可 |
| B 级 | 可抽象复用 | 保留结构与方法，替换项目路径和对象 |
| C 级 | 仅当前项目可用 | 仅保留为项目技能，不建议外迁 |

### 6.1 A 级资产

- 顶层治理文件模型
- 知识图谱与域索引机制
- WAL 机制与模板
- 生命周期与门禁
- 通用治理技能
- 通用分析/生成技能骨架
- 版本化升级思路

### 6.2 B 级资产

- 列表页骨架技能
- 组件选型技能
- 表格列渲染规范
- 弹窗/抽屉配方
- AI 渲染管线规范

### 6.3 C 级资产

- 直接引用当前项目特有路径的组件清单
- 直接写死当前项目组件实现细节的示例
- 当前项目内的具体业务专题 wiki

## 7. 当前工程最值得推广的 10 个设计点

1. 将提示词工程视为仓库工程，而不是聊天附件。
2. 用单一来源目录管理所有规则和知识资产。
3. 将总索引做成图谱，而不是做成长说明。
4. 用域化知识结构组织 wiki。
5. 用 WAL 先写后并，减少冲突。
6. 用 MEMORY 只保留高频稳定摘要。
7. 用 skills 与 self_skills 双层分治。
8. 用模板标准化范围控制和写回动作。
9. 用 CHANGE_LOG 记录提示词工程自身变更。
10. 用 versions 支撑补丁式升级。

## 8. 当前工程仍可继续加强的点

虽然整体设计已经较成熟，但仍有一些可以继续加强的地方：

### 8.1 脚本与目录一致性

- 当前治理脚本存在路径命名不一致风险。
- 建议补一份“治理脚本自检清单”。

### 8.2 技能之间的关联显式化

- 当前索引已存在，但技能间的“上下游关系图”仍可继续强化。
- 建议后续补一份技能依赖图或技能调用链图。

### 8.3 模板参数化程度

- 一些模板已存在，但仍偏静态文档。
- 后续可继续将高频模板做成参数化 schema。

### 8.4 治理脚本接入 CI

- 当前已有脚本基础。
- 后续可把 wiki linter、索引一致性检查接入 CI 或 pre-commit。

## 9. 面向新项目的抽取策略

如果要从当前项目抽一份通用工程，请按下面顺序处理：

1. 先复制顶层治理文件模型
2. 再复制 `wiki/` 的图谱与域结构
3. 再复制 WAL 模板
4. 再复制治理类技能
5. 再挑选通用分析/生成技能
6. 最后根据新项目重建 `self_skills/`

不要反过来做。因为项目技能只有在通用骨架稳定后才有意义。

## 10. 最终结论

`fupan-client` 当前的 `agent/` 已经不是“提示词合集”，而是一个具备下列能力的提示词工程系统：

- 有角色层
- 有索引层
- 有知识层
- 有技能层
- 有治理层
- 有演化层

从复用角度看，最值得抽取的是“工程化方法与结构”，其次是“通用治理技能”，最后才是“项目配方式技能”。

也就是说，真正可迁移的核心不是某句 prompt，而是这套“如何组织 prompt、知识、技能、记忆与治理”的完整方法论。
