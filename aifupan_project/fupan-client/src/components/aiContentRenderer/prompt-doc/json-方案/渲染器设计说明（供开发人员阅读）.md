# 混合 JSON 渲染器设计说明

## 1. 概述

本渲染器当前仍兼容混合内容，但推荐上游模型默认输出结构化 JSON，而不是“Markdown 字符串包一层 JSON”。

渲染器的目标是：

1. 当检测到完整 JSON 行时，先把 JSON 转成 HTML
2. JSON 文本节点中的换行、加粗、斜体、行内代码等基础 Markdown 语义需要被保留
3. 再把“转换后的 HTML + 原始 Markdown 文本”一起交给 `mdFormat`
4. 当 JSON 暂时不完整时，不把协议噪音输出到页面，只提取正文文案做临时预览
5. 当 JSON 后续补全后，重新解析并用正式 HTML 替换预览

## 2. 总体思路

新的渲染链路如下：

1. 接收原始文本
2. 按换行拆分
3. 逐行识别当前行是否像 JSON
4. 若是完整 JSON：先转成 HTML 片段
5. 若是不完整 JSON：提取 `value/title/content/text` 等字段文案
6. 将 Markdown 行与 JSON 转换后的 HTML 片段重新拼接
7. 将拼接结果统一交给 `mdFormat`
8. 输出最终 HTML

## 3. 核心模块

### 3.1 混合内容解析器

负责按行扫描原始文本，并区分三类内容：

- 普通 Markdown 行
- 完整 JSON 行
- 不完整 JSON 缓冲段

### 3.2 JSON 缓冲区

用于暂存疑似 JSON 但尚未解析成功的内容。

行为规则：

- 新的一行如果明显像 JSON 开头，则进入缓冲区
- 缓冲区拼接后如果 `JSON.parse` 成功，则按结构化内容渲染
- 如果仍未成功，但仍像 JSON 延续内容，则继续等待
- 如果已不再像 JSON 延续内容，则输出缓冲区中的正文预览，并清空缓冲

### 3.3 BlockRenderer

负责把结构化 JSON 转换为 HTML 字符串，并保留文本节点中的基础排版语义。

当前支持：

- `div`
- `h1 ~ h6`
- `p`
- `ul`
- `ol`
- `li`
- `blockquote`
- `pre`
- `table`
- `hr`
- `Progress`
- `Card`
- `Alert`
- `Statistic`
- `Tag`
- `Timeline`
- `Collapse`
- `Chart`

补充要求：

- 文本节点中的换行需要保留
- 文本节点中的 `**加粗**`、`*斜体*`、`` `代码` `` 等基础 Markdown 行内语义需要保留
- 推荐模型直接输出 `strong/em/code/br/p/li` 等结构，不要把 Markdown 原文包在文本字段里

### 3.4 Markdown 二次过滤器

JSON 转 HTML 后，不直接终态输出，而是把结果插回原文，再统一调用 `mdFormat`。

这样做的目的是：

1. 支持 Markdown 与 JSON 混排
2. 让 Markdown 语法继续生效
3. 让 HTML 块通过 `mdFormat` 做统一二次处理

## 4. 逐行解析流程

### 4.1 第一步：按换行拆分

将原始内容统一转成 `\n` 换行，再按换行拆成数组。

### 4.2 第二步：识别 JSON 行

当某一行满足以下条件之一时，视为疑似 JSON：

- 以 `{` 或 `[` 开头
- 以 `data:{` 或 `data: {` 开头
- 包含 `"type"`、`"component"`、`"blocks"`
- 包含明显的 JSON 键值特征，例如 `":`

### 4.3 第三步：优先解析完整 JSON

对疑似 JSON 的内容尝试以下处理：

1. 整行直接 `JSON.parse`
2. 若整行失败，尝试截取行内完整的 `{...}` 或 `[...]`
3. 解析成功后，判断是否是以下结构：
   - 单个 Block
   - `{"blocks":[...]}`
   - `{"type":"fragment","block":{...}}`
   - `{"type":"done","meta":{...}}`

只要满足上述结构之一，即执行 HTML 渲染。

### 4.4 第四步：不完整 JSON 预览

如果当前内容明显是 JSON，但还无法成功解析：

- 阻止输出原始 JSON 协议文本
- 优先提取以下字段中的文案内容：
  - `value`
  - `title`
  - `content`
  - `text`
  - `label`
  - `name`
  - `description`
- 提取到的文案作为临时预览输出
- 若提取不到文案，则暂不展示该 JSON 片段

### 4.5 第五步：重新走 Markdown 渲染

将以下内容重新拼回一个字符串：

- 原有 Markdown 行
- JSON 渲染后的 HTML 片段
- JSON 不完整时提取出的正文预览

最终统一调用 `mdFormat`，输出最终 HTML。

### 4.6 文本节点渲染要求

对于 JSON 内部文本内容：

1. 不能只做纯转义输出
2. 需要保留换行
3. 需要保留行内加粗、斜体、代码、链接等基础样式
4. 若文本字段本身仍含有 Markdown 痕迹，渲染器应尽量保留其可视化效果

## 5. 为什么要先转 JSON 再走 mdFormat

原因如下：

1. AI 返回内容可能包含历史兼容格式
2. JSON 生成的 HTML 需要和 Markdown 正文一起排版
3. `mdFormat` 已经是现有渲染链路的一部分，保留它能降低改造范围
4. 先转 HTML，再走 `mdFormat`，可以让混合文本在同一套渲染结果里落地
5. 即使上游偶尔仍输出 Markdown 痕迹，渲染器也应尽量保留换行和基础样式

## 6. 深度思考内容

深度思考内容仍需独立维护一份渲染链路，但解析方式与正文一致：

1. 单独累积 thinking 文本
2. 调用同一个混合解析器
3. 最终包装在 `.deepThinkingTitle` 与 `.deepThinking` 容器中

## 7. 兼容场景

### 7.1 纯 Markdown

如果整段内容都不是 JSON，则直接按 Markdown 处理。

### 7.2 纯 JSON

如果整段内容本身就是一个完整 JSON 对象或 JSON 数组，则直接进行结构化渲染。

### 7.3 Markdown 与 JSON 混排

如果正文中间夹杂完整 JSON 行，则 JSON 行先转 HTML，再与 Markdown 一起进入 `mdFormat`。

### 7.4 半截 JSON

如果流式输出过程中 JSON 尚未补全，则只输出可提取的正文，不输出 JSON 协议噪音。

## 8. 安全要求

- `a.href` 仅允许 `http`、`https`、`mailto`
- 纯文本内容不能只做转义，还要兼顾基础 Markdown 行内语义保留
- `style`、`class` 等属性输出需经过最基本转义
- 不允许把原始半截 JSON 直接塞给 `innerHTML`

## 9. 实现落点

当前实现建议统一收敛到独立解析器文件，由它提供一个统一入口，例如：

```javascript
renderAiResponseContent(content, {
  thinkingContent
})
```

并在以下场景复用：

- 流式实时预览
- 最终回答内容落地
- 历史记录回显
- JSON 格式纠正后的二次展示

## 10. 最终结论

新的解析器不是“只识别 JSON”，也不是“只渲染 Markdown”，而是“先解析结构化 JSON，再与 Markdown 通道协同渲染”。

一句话总结：

先拆行识别 JSON，完整 JSON 转 HTML，文本节点保留换行和基础样式，不完整 JSON 提取正文，最后统一交给 `mdFormat`。
