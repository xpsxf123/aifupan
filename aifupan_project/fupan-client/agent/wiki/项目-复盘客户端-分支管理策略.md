# 分支管理策略（fupan-client）

## 通用分支模型

| 分支前缀 | 用途 | 对应环境 | 说明 |
|----------|------|---------|------|
| `dev` | 开发分支 | 本地开发环境 | 新功能开发默认使用 |
| `test` | 测试分支 | 测试环境 | 功能修改/缺陷修复默认使用 |
| `release` | 预发布分支 | 预发布环境（≈线上） | 线上紧急 Bug / 特殊情况使用 |

### 场景对应规则

| 场景 | 默认分支 |
|------|---------|
| 新开功能 | `dev` |
| 修改功能 / 修复 Bug | `test` |
| 线上紧急 Bug / 特殊情况 | `release` |

## fupan-client 特殊规则（带版本号）

fupan-client 的分支格式为 `{prefix}-{version}`，例如：
- `dev-2.6.0.8`
- `test-2.6.0.8`
- `release-2.6.0.8`

### 当任务只指定版本号，未指定前缀时的优先级

```
release > test > dev
```

执行逻辑：
1. 优先检查 `release-{version}` 是否存在
2. 若不存在，检查 `test-{version}`
3. 若不存在，检查 `dev-{version}`
4. 从找到的最高优先级分支切一个 `aidev-YYYYMMdd-NO` 分支进行开发

### 示例

- 任务说"在 2.6.0.8 分支上开发"
- 检查顺序：`release-2.6.0.8` → `test-2.6.0.8` → `dev-2.6.0.8`
- 以找到的最高优先级分支为基础创建开发分支

## 四层环境分支（从低版本 → 高版本）

| 层级 | 标识 | 分支名 | 环境 | 说明 |
|------|------|--------|------|------|
| 1（最低） | dev | `dev-{version}` | 本地开发环境 | 新功能最先在这里开发 |
| 2 | test | `test-{version}` | 测试环境 | 功能经过测试后合入 |
| 3 | release | `release-{version}` | 预发布环境 | 接近线上环境 |
| 4（最高） | prod | `master/main` | 生产环境 | 已发布的线上版本 |

## 分支选择与开发流程（代码开发任务专用）

### 准备工作流（每次代码开发前必须执行）

```
① 解析任务中的分支信息
   ├─ 有明确分支 → 切换到该分支
   ├─ 有版本号无前缀 → 按 release>test>dev 查最高优先级分支
   └─ 无任何分支说明 → 使用当前项目分支

② 查询 wiki 知识库 → agent/wiki/ 下当前分支的相关信息
   ├─ 有相关信息 → 参考知识库内容开发
   └─ 无相关信息 → 自动从最低版本分支开始查

③ 查询功能是否存在（从上往下查: prod → release → test → dev）
   ├─ 查到某层有该功能 → 在该层开发
   └─ 全部无 → 从最低版本分支开始开发

④ 创建 aidev 分支（如需要）
   └─ git checkout -b aidev-YYYYMMdd-NO
```

### 修改方向规则

| 变更类型 | 开发起点 | 合并方向 |
|---------|---------|---------|
| 简单修改（文案等） | 最低版本分支 | 从低 → 高合并 |
| 新功能开发 | 最低版本分支 | 从低 → 高合并 |
| 功能修改/Bug 修复 | 按功能存在层级确定 | 从低 → 高合并 |

### ⚠️ 红线规则

> **严禁从高版本分支切低版本功能分支。**
>
> 如果一个功能需要在低版本上开发，必须从低版本分支切出开发分支，开发完成后从低到高逐一合并。
> 从高版本切分支会导致合并冲突，因为高版本已有低版本不存在的代码。

### 分支开发示例

```
场景：需要在 2.6.0.8 上开发一个新功能

✅ 正确的做法：
   git checkout dev-2.6.0.8
   git checkout -b aidev-20260720-01
   # 开发...
   git commit -m "feat: xxx"
   git push origin aidev-20260720-01
   # 合并到 dev-2.6.0.8 → test-2.6.0.8 → release-2.6.0.8（按需）

❌ 错误的做法：
   git checkout release-2.6.0.8
   git checkout -b aidev-20260720-01
   # 问题：新功能在低版本上可能不存在依赖，合并时会冲突
```

## 其他项目通用规则

对于非 fupan-client 项目，如未特殊说明：
- 分支名不加版本号后缀
- 直接使用 `dev`、`test`、`release`
- 分支选择逻辑同上（优先级 release > test > dev）

## 版本开发目录

### 概述

`dev-X.Y.Z.W` 微分支（功能开发分支）的变更记录统一存放在 `docs/版本开发目录/` 下，按大版本号（X.Y.Z）组织为独立文件。

### 文件结构

```
docs/版本开发目录/
├── README.md           # 目录说明
├── 2.6.2.md            # 大版本 2.6.2 的开发记录
├── 2.6.3.md            # 大版本 2.6.3 的开发记录
└── ...
```

- 文件命名规则：`<大版本号>.md`（如 `2.6.2.md`）
- 每个大版本文件记录该版本下所有 `dev-X.Y.Z.W` 微分支的功能信息

### 文件记录格式

每个微分支记录包含：功能名称、变更时间、变更文件列表、功能描述、合并状态。

**示例：**

```markdown
# dev-2.6.2 大版本开发记录

---

## 2.6.2.1 分支
**功能名称**：巨量+来客授权统一选择组件

**变更时间**：2026-07-30

**变更文件**：
- src/components/liveRoomAuthorizeDialog.vue（新增）
- src/views/modules/dataAnalysis/component/allAnchors.vue

**功能描述**：
封装授权方式统一入口组件，支持弹窗/按钮两种模式。

**合并状态**：已合并至 test-2.6.2

---

## 2.6.2.2 分支
**功能名称**：商品数据 Tab 及空态逻辑

...（类似格式）
```

### AI 自动维护规则

| 时机 | 操作 |
|------|------|
| 进入 `dev-X.Y.Z.W` 分支 | 检查 `docs/版本开发目录/X.Y.Z.md` 是否存在，不存在则创建；检查当前功能分支是否已记录，未记录则追加空模板 |
| 每次提交代码 | 更新 `docs/版本开发目录/X.Y.Z.md` 中当前功能分支的变更文件列表和功能描述 |
| 合并 dev → test/reslease | 将 `合并状态` 更新为 `已合并至 test-X.Y.Z` 或 `已合并至 reslease-X.Y.Z` |

### 重复分支冲突检测

在 `dev-X.Y.Z.W` 分支上执行任务前，AI 会自动检测同一大版本下其他 `dev-*` 微分支是否修改了相同的文件。若存在重叠，将暂停任务并提醒用户确认。`aiDev-*` 分支不触发此检测。

## 版本变更与版本功能明细

### 版本变更文件

`test-X.Y.Z` 和 `reslease-X.Y.Z` 分支的代码变更统一记录在 `docs/版本变更/X.Y.Z.md` 中，格式为「变更明细」表格，每行包含：记录时间、功能变更标题、功能变更模块、功能变更文件、功能变更详细内容。

### 版本功能明细

每个 `docs/版本变更/X.Y.Z.md` 文件在「变更明细」表格之后，包含一个「**版本功能明细**」章节。

**用途：** 以功能视角列出当前版本的完整功能清单，供测试团队作为测试验收清单使用。

**内容规则：**
- 不记录"改了什么"（那是变更明细表格的职责），只记录"当前版本有哪些功能"
- 每个功能一行，包含序号、功能名称、功能概述、涉及模块
- 若功能在后续版本中被移除，标记为 `~~已移除~~`
- 若功能是继承自上一版本（未改动），也应在明细中列出，确保清单完整

**维护规则：**

| 场景 | 操作 |
|------|------|
| dev 分支合并到 test/reslease（新功能） | 新增一行 |
| 功能从当前版本移除 | 标记 `~~已移除~~` 或删除 |
| 功能更新/增强 | 更新对应「功能概述」 |
| 上一版本继承功能（未改动） | 保留不标记 |

**AI 自动维护时机：**
- dev 分支合并到 test/reslease 时，自动从 `docs/版本开发目录/X.Y.Z.md` 读取功能描述，追加到版本功能明细
- 在 test/reslease 分支直接修改功能时，同步更新版本功能明细中对应的概述
