# 任务拆解指南

## 技能目的
- 把“模糊需求”变成可执行的子任务队列，降低实现与验收风险
- 强制每个子任务都有：输入、输出、验收点、回滚点
- 支持并行：能拆就拆，避免一个任务吞掉全部复杂度

## 输入参数
- `goal`：必填，文本。用户的目标/需求描述
- `constraints`：选填，列表。已知约束（技术栈、目录结构、权限、接口契约、禁用项）
- `context_links`：选填，列表。可用参考（PRD/原型/wiki 页面/代码入口）
- `risk_level`：选填，枚举。`low` | `medium` | `high`（默认 `medium`）

## 输出
- `overview`：一句话描述本次交付的范围边界
- `task_list`：子任务列表（按执行顺序）
- `parallel_groups`：可并行子任务分组（若适用）
- `acceptance_checklist`：总体验收清单
- `open_questions`：待确认项（阻塞/非阻塞分组）

## 子任务格式（强制）
每个任务必须包含：
- `id`：数字或短字符串
- `name`：一句话任务名
- `purpose`：为什么需要做
- `inputs`：输入数据/前置条件/依赖文档
- `outputs`：产出物（文件/接口/页面/文档）
- `acceptance`：可验证的验收点（尽量可在本地复现）
- `rollback`：可回滚方式（删文件/开关/降级）

## 拆解规则（推荐）
- 先切“垂直链路”：按用户旅程/页面路径/路由入口拆
- 再切“横向能力”：接口契约、状态管理、组件沉淀、错误处理、埋点/日志
- 风险高的先行：先做原型验证/契约对齐/最小跑通，再扩展
- 禁止把“写文档/实现/验收”混成一个任务：至少拆成 2-3 个

## 适用场景
- 多页面联动、接口改造、权限/路由变更、状态共享策略调整
- AI 产出需要可验收与可回滚的复杂改动

## 边界
- 不臆造接口字段、枚举、权限规则；不确定必须进入 `open_questions`
- 不做大范围重构；拆解应优先增量接入并可回滚
