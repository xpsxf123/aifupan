# 前端智能接口对接调试助手

本技能用于“低侵入、可复用、可联调”的前端接口对接：在尊重项目现有 HTTP 封装与接口管理方式的前提下，基于接口文档完成 API 定义、页面接入、Mock 策略、错误处理与数据转换，并输出可交付的对接清单与测试要点。

参考文档：`.trae/doc/前端智能接口对接助手.md`

参考规则：

- `.trae/rules/http-rules.md`
- `.trae/rules/project-rules.md`

## 1. 何时调用

当用户提出以下诉求之一时调用本技能：

- “根据接口文档把某个模块/页面对接起来”
- “已有静态页面/交互稿/脑图，帮我把接口接上并联调”
- “需要加 Mock 开关、统一错误处理、数据格式化、CRUD 刷新联动”

## 2. 输入材料（由少到多，默认只用接口文档也可完成）

### 2.1 必需（最低可用）

- 接口文档（URL、方法、参数、响应结构、错误码、鉴权方式）

### 2.2 可选（用于提升“交互完整度/逻辑纠错能力”）

- 需求文档：字段含义、业务规则、边界条件、权限控制、成功/失败提示文案
- 交互说明/原型：加载态、空态、分页、弹窗/抽屉、二次确认、提交后回跳/刷新
- 脑图/流程图：页面流转、接口依赖（新增/编辑/删除后如何刷新）、状态机
- 前端静态页面代码：组件结构、表单字段、列表列定义、现有 hooks/组件复用点

### 2.3 冲突处理优先级

- 接口文档（真实可调用性） > 交互/需求（体验与规则） > 静态页面（当前实现现状）

## 3. 执行流程（必须先分析后执行）

### 3.1 项目现状分析（先做“发现”，不做“重构”）

1. HTTP 封装层

- 定位封装入口：`src/http/index.js` 与 `src/http/httpConfig/`
- 识别现有实例：`httpBack` / `httpClient` 是否齐全；baseURL 规则；timeout；header 注入（token）
- 识别响应解构与错误处理：成功码、错误码统一提示、401 跳转登录等
- 识别是否已有 Mock 能力：环境变量/请求配置标记/本地 mock-server

2. 接口管理方式

- 定位 API 目录：`src/http/api/` 与聚合导出 `src/http/api/index.js`
- 识别模块组织：按业务模块拆分、`export default { ... }` 的导出形态、JSDoc 规范

3. 数据处理方式

- 是否已有通用格式化工具（时间、金额、枚举映射）
- 字典/枚举的来源（后端下发/前端常量/配置化）

4. 页面与状态管理

- Pinia 是否已有对应模块 store；若缺失则按现有风格补齐
- 列表页/表单页（弹窗、抽屉、独立页）之间如何同步刷新

### 3.2 接口对接规划（输出映射表，再开始写代码）

1. 接口清单与页面映射

- 每个页面/组件对应哪些接口（查询/新增/修改/删除/详情/导入导出）
- 标注接口依赖关系（新增成功 -> 刷新列表；删除成功 -> 处理分页回退）

2. Mock 策略

- 新接口优先 Mock：但禁止在正式 API 文件里内联 `setTimeout/写死数据`
- Mock 的正确落点：独立 mock 数据模块 + 统一开关（环境变量或请求配置标识），由 HTTP 层或请求适配层接管

3. 错误处理分层

- 公共错误：HTTP 响应拦截器统一处理（如 401、通用非 200、网络异常）
- 业务错误：在页面/业务调用处处理（如“库存不足”“重复提交”），并给出对应交互反馈

4. 数据转换策略

- 明确字段级规则（时间格式、金额千分位、状态码映射、空值处理）
- 明确转换位置：优先放在 utils/format 或模块级 formatter，避免散落在模板中

### 3.3 代码补全执行（最小侵入）

按以下优先级扩展，避免大范围重构：

1. 扩展 HTTP 封装（仅当缺能力时）

- 补齐 `httpClient`（若项目规则要求且项目中不存在）
- 增加 Mock 切换能力（若项目无 Mock 机制）：通过环境变量/请求配置标记控制路由到 mock 数据
- 统一错误处理：保持现有逻辑不变，在合适位置补齐分层处理

2. 组织 API 定义（必须遵守项目规则）

- 在 `src/http/api/{module}.js` 内按模块定义方法，`export default { ... }`
- 严禁在组件内直接导入 axios 或 httpConfig 发请求
- GET 使用 `{ params }`；POST/PUT 直接传参
- 每个方法必须写 JSDoc：`@description`、`@param`、`@returns`
- 在 `src/http/api/index.js` 聚合导出模块

3. Mock 数据（可切换、可移除）

- Mock 数据结构必须严格遵循接口文档响应结构
- Mock 文件应独立可删除，不影响正式接口调用

4. 页面接入与联动

- 列表：初始化加载、筛选查询、分页切换、刷新、loading、空态
- 表单：回显、提交（新增/编辑）、成功提示、关闭弹窗/抽屉、触发列表刷新
- 删除：必须优先使用 `el-popconfirm` 做二次确认，成功后刷新并处理“当前页空了回退上一页”

## 4. 调试与联调指南（输出“可定位问题”的动作）

### 4.1 网络层快速定位

- 请求未发出：检查 API 方法是否被正确调用、参数是否按 GET/POST 规范传递、baseURL 是否正确
- 401/跳登录：检查 token 注入与后端鉴权协议是否一致（Bearer/字段名/过期处理）
- 接口成功但页面无数据：核对响应结构映射（如 `res.data.list` vs `res.list`），避免错误解构

### 4.2 响应结构与错误码对齐

- 明确“成功判定”：`code === 200` 或后端约定的其他码
- 公共错误统一提示，业务错误在调用处处理并补齐交互（按钮 loading、表单校验提示）

### 4.3 CRUD 常见边界

- 删除后列表为空：自动回退页码并重新拉取
- 快速重复提交：禁用按钮/防抖/以 loading 状态锁定
- 弹窗关闭后刷新：以事件/回调或状态驱动刷新，避免手动操作 DOM

## 5. 交付物（每次对接完成必须输出）

- 修改文件清单：新增/修改文件路径 + 每个文件做了什么
- 接口对接映射表：页面/组件 -> 接口列表 -> 类型 -> Mock 启用方式
- 关键实现说明：Mock 开关、错误处理分层、数据转换策略
- 测试要点建议：核心路径 + 边界场景（分页回退、表单校验、错误码、空态/加载态）

## 6. 用户输入模板（建议引导用户按此提供信息）

请提供以下内容（至少提供接口文档即可）：

1. 接口文档：模块名 + 接口清单（URL/方法/参数/响应/错误码）
2. 需求文档（可选）：字段规则、权限点、提示文案
3. 交互说明/原型（可选）：列表/表单/弹窗/抽屉的操作流程
4. 脑图/流程图（可选）：页面流转、接口依赖、刷新链路
5. 前端页面/组件路径（若已有静态代码）
