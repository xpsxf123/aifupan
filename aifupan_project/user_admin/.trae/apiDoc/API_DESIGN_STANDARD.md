# 后端接口设计与数据交互规范

本文档定义了当前项目后端接口的路径命名规则、通用响应数据结构以及分页数据交互格式。前后端开发人员需严格遵守此规范进行对接。

---

## 一、 接口路径命名规则

为了保证接口的统一性和安全性，所有的 API 路径需遵循以下规则：

1. **统一风格**
   - 接口路径统一使用小写字母。
   - 多个单词之间使用连字符 `-` 进行分隔（kebab-case），例如：`/sub-company`。

2. **【强制】禁止使用 Path 变量传参**
   - **绝对不允许在 URL 路径中使用动态变量传参**（例如：~~`/menu/delete/{id}`~~ 是**被禁止**的）。
   - 所有的参数传递必须通过 **Query String**（如：`/menu/detail?id=1`）或者 **Request Body** 传递。

3. **操作动词后缀**
   - 由于禁止了 RESTful 风格中的 Path 传参，针对资源的特定操作，必须在路径末尾明确加上操作动词，以区分不同的意图。
   - 常用的标准后缀如下：
     - `/add`：新增数据 (POST)
     - `/update`：修改数据 (POST)
     - `/delete`：删除数据 (POST，参数放 Body 中)
     - `/detail`：查询单条详情 (GET)
     - `/list`：分页列表查询 (POST)

4. **模块层级**
   - 标准格式为：`/{模块名}/{资源名}/{操作}`
   - 示例：`/api/governance/sub-company/add`

## 二、 全局响应数据格式 (ApiResponse)

所有的后端接口均统一包装为 `ApiResponse<T>` 格式的 JSON 返回。前端需首先判断 `code` 字段是否为 `0` 来决定业务是否成功。

### 基础响应字段说明

| 字段名      | 类型       | 必含 | 描述         | 备注                                                           |
| :---------- | :--------- | :--- | :----------- | :------------------------------------------------------------- |
| `code`      | Integer    | 是   | 响应状态码   | `0` 表示业务处理成功；非 `0` (如 `500`) 表示业务处理失败       |
| `msg`       | String     | 是   | 提示消息     | 成功时通常为 "请求成功"，失败时为具体的错误原因说明            |
| `data`      | Object (T) | 否   | 业务数据体   | 请求成功时返回的具体业务数据。泛型 `T` 视具体接口而定          |
| `exception` | String     | 否   | 异常堆栈信息 | 发生异常时返回的错误堆栈信息，通常仅用于开发或测试环境排查问题 |
| `timestamp` | Long       | 是   | 时间戳       | 后端处理该次请求的 Unix 时间戳 (毫秒级)                        |
| `extend`    | Map        | 否   | 额外扩展参数 | 用于返回一些非标准的、可扩展的附加键值对数据                   |

**成功响应示例:**

```json
{
  "code": 0,
  "msg": "请求成功",
  "data": {
    "id": 1,
    "name": "示例数据"
  },
  "timestamp": 1731234567890
}
```

## 三、 分页数据交互规范

### 1. 分页请求参数 (PageRequest)

当接口涉及分页查询时，请求体 (Request Body) 需包含以下基础分页参数：

| 字段名  | 类型    | 默认值 | 描述                         |
| :------ | :------ | :----- | :--------------------------- |
| `page`  | Integer | `1`    | 当前请求的页码，最小为 1     |
| `limit` | Integer | `10`   | 每页显示的数据条数，最小为 1 |

### 2. 分页响应数据 (PageData)

当接口返回分页列表数据时，`ApiResponse` 中的 `data` 字段结构将被固定为 `PageData<T>`。

| 字段名       | 类型    | 描述     | 备注                                                    |
| :----------- | :------ | :------- | :------------------------------------------------------ |
| `currPage`   | Long    | 当前页码 | 对应请求中的 `page`，若传入异常值后端会自动修正为 `1`   |
| `pageSize`   | Long    | 页大小   | 对应请求中的 `limit`，若传入异常值后端会自动修正为 `10` |
| `totalCount` | Long    | 总记录数 | 满足查询条件的记录总数                                  |
| `totalPage`  | Long    | 总页数   | 根据 `totalCount` 和 `pageSize` 计算得出，最小为 `1`    |
| `list`       | List<T> | 数据列表 | 当前页的实际业务数据数组集合                            |

**分页响应示例:**

```json
{
  "code": 0,
  "msg": "请求成功",
  "data": {
    "currPage": 1,
    "pageSize": 10,
    "totalCount": 25,
    "totalPage": 3,
    "list": [
      { "id": 1, "name": "Item 1" },
      { "id": 2, "name": "Item 2" }
    ]
  },
  "timestamp": 1731234567890
}
```
