技能定位本技能是一个高灵活性、低侵入性的前端接口对接指导工具。它不预设具体的代码实现方式，而是通过逻辑描述和功能要求，引导AI模型：

阅读理解项目现有的HTTP封装、接口管理、数据处理等基础设施

分析识别项目中已有的代码组织模式和编码规范

按需补全接口对接相关的代码，保持与现有项目风格一致

适用场景当用户提供以下资料并请求完成前端接口对接时触发：

需求拆分文档

业务流程图/交互脑图

前端静态页面代码

后台接口文档

项目现有的HTTP请求封装文件（如有）

核心原则原则一：尊重现有架构必须先阅读和分析项目现有的HTTP请求封装方式（如request.js、http.js、api.ts等）

理解当前项目的请求拦截器、响应拦截器、错误处理机制

识别项目现有的接口管理方式（集中管理、模块化管理、还是组件内直接调用）

保持与现有代码风格、命名规范、目录结构的一致性

原则二：最小侵入性尽可能复用和扩展现有的封装逻辑，避免大规模重构

新增功能模块时，遵循项目现有的组织方式和命名习惯

如果需要新增配置文件或工具函数，放置在项目现有类似功能文件所在的位置

原则三：智能适配根据项目现有技术栈（Vue2/Vue3/React等）选择相应的实现方式

根据项目现有状态管理方案（Vuex/Pinia/Redux等）决定接口数据的存储方式

根据项目现有的UI组件库（Element UI/Ant Design等）选择合适的提示反馈方式

执行流程第一步：项目现状分析在开始对接前，AI需要先完成以下分析：

HTTP封装层分析

找到项目中HTTP请求的封装文件位置

分析请求拦截器中做了什么（如：添加token、请求参数处理）

分析响应拦截器中做了什么（如：统一错误处理、数据解构）

识别当前是否已有Mock处理机制

接口管理方式分析

查看项目中接口是如何管理的（独立api文件夹、按模块拆分、还是组件内直接调用）

了解接口配置的写法（统一配置对象、还是函数封装）

是否存在公共的错误码映射表

数据处理方式分析

项目中是否有通用的数据格式化工具函数

是否存在数据转换的规范（如时间处理、金额格式化）

枚举值、字典数据的管理方式

组件通信与状态管理分析

页面间如何共享数据

列表页和表单页的通信方式

刷新列表、重置表单等常见操作的实现模式

第二步：接口对接规划基于需求文档和接口文档，输出对接规划：

接口清单与映射

列出每个页面/模块需要对接的接口

标注每个接口的类型（查询、新增、修改、删除）

识别接口之间的依赖关系（如删除后需刷新列表）

Mock策略确定

新接口：优先采用Mock方式

老接口：保持原有方式

如何区分：根据项目现有Mock机制，设计一个轻量级的开关方式（如通过环境变量、接口配置中的标识位）

错误处理分层

公共错误码：应在HTTP拦截器中统一处理（如401跳转登录、500提示服务器错误）

独立业务错误码：应在具体调用处处理，根据业务需求给出相应提示

识别接口文档中哪些是公共错误码，哪些是独立错误码

数据转换需求

梳理需要格式化的字段（时间、金额、枚举值等）

明确转换规则（时间格式、数字格式、状态映射等）

确定转换的实现位置（组件内、工具函数、还是拦截器）

第三步：代码补全执行按照以下逻辑进行代码补全：

扩展HTTP封装（如需要）

如果项目尚无Mock机制，在请求拦截器中增加根据标识切换Mock的逻辑

如果项目尚无公共错误码处理，在响应拦截器中增加统一处理

保持现有拦截器逻辑不变，在适当位置增加新功能

组织接口定义

按照项目现有的接口管理方式，创建或补充接口定义

新接口定义中包含：URL、请求方法、是否Mock、Mock数据路径等必要信息

Mock数据严格遵循接口文档的响应结构

实现数据转换

如果项目有通用格式化工具，直接复用

如果没有，创建轻量级的转换函数，放置在项目的utils目录下

转换函数支持配置化，便于后续维护

接入组件

在静态页面组件中引入接口定义

实现接口调用逻辑，注意：

列表页：初始化加载、筛选查询、分页切换、刷新列表

表单页：数据回显、提交新增/修改、成功后回调

删除操作：二次确认、成功后刷新列表

处理好加载状态（loading）和错误提示

处理接口关联关系

新增/修改/删除成功后，自动刷新列表数据

如果列表支持分页，删除后需检查当前页数据是否为空，若为空则跳到上一页

表单提交成功后，关闭弹窗/抽屉，并给出成功提示

修改文件清单

列出所有修改或新增的文件路径

简要说明每个文件的修改内容

接口对接映射表

页面/组件名称

对接的接口列表

接口类型

Mock启用状态

关键代码说明

重点说明新增的Mock控制逻辑

说明错误处理的分层实现

说明数据转换的实现方式

测试要点建议

列出需要重点测试的场景

提示可能的边界情况

执行示例（文字描述）用户输入示例：

我有一套用户管理模块的前端代码，现有HTTP封装在src/utils/request.js中，接口文档见附件。请帮我完成用户列表和用户新增/编辑功能的接口对接。新接口优先使用Mock方式，时间字段要转为年月日格式，金额字段要转为千分位格式。

AI执行思路：

首先阅读src/utils/request.js，了解：

当前请求使用axios，有请求拦截器添加token

响应拦截器只做了数据解构，没有统一错误处理

没有Mock机制

分析现有代码结构：

接口定义在src/api/user.js中，每个接口是一个独立函数

时间格式化使用src/utils/format.js中的formatDate函数

组件采用Vue3 Composition API

确定实施方案：

在request.js的请求拦截器中增加Mock判断逻辑：如果接口配置中mock=true，则返回Mock数据

在src/api/user.js中新增接口函数，每个函数包含一个mock参数控制是否使用Mock

创建src/mock/user.js存放Mock数据，遵循接口文档格式

在src/utils/format.js中增加数字千分位格式化函数

在组件中调用接口函数，处理好加载状态和错误提示

代码补全：

修改request.js，增加Mock适配逻辑

新增src/mock/user.js，包含列表、新增、编辑、删除的Mock数据

扩展src/api/user.js，添加新接口函数

修改用户列表组件，接入列表查询接口，并对时间和金额字段应用格式化

修改用户表单组件，接入新增/编辑接口，并在成功回调中触发列表刷新

输出交付物：

修改文件清单及说明

接口对接映射表

关键代码片段说明

技能约束必须先分析后执行：在修改任何代码前，必须先阅读理解项目现有结构和规范

保持原有风格：新增代码的命名、写法、组织方式必须与项目现有代码保持一致

最小改动原则：优先通过扩展现有函数/组件的方式实现，避免大范围重构

Mock数据真实性：Mock数据结构必须严格遵循接口文档，确保前端联调时无缝切换

错误提示友好性：所有错误提示应使用项目现有的消息提示组件，保持体验一致

适用项目类型Vue2/Vue3项目（Vuex/Pinia）

React项目（Redux/Context）

原生JavaScript项目

任何有明确HTTP封装层的前端项目
