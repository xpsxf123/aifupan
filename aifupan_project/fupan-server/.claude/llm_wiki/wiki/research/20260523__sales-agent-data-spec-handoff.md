# 销售智能体客户行为信号数据接口 — 设计稿

**版本：** v0.1（提案待评审）
**日期：** 2026-05-23
**适用方：** SalesCoach 销售智能体团队
**目的：** 为销售智能体补充客户的"产品使用行为信号"，使其能依据"客户用了什么 / 没用什么"分流话术策略：**关键行为缺失 → 推动销售主动触达；关键行为已发生 → 作为深度沟通的话术切口。**

---

## 1. 背景与目标

### 1.1 现状

销售智能体当前可拿到的客户数据集中在**基础画像与跟进进程**：基础资料、跟进记录、阶段事件、AI 画像、订单生命周期。可回答"客户是谁 / 跟到哪一步 / 买了什么"。

### 1.2 缺口

当前数据无法回答两个对话术决策关键的问题：

- **客户的产品激活深度**：账号规模、是否使用过核心功能
- **客户的资源投入度**：分析时长、算力消耗

这两组信号是判断"沉睡客户需 push 唤醒"还是"活跃客户可深聊变现"的核心依据。

### 1.3 目标

新增一个客户行为信号查询接口，单次最多查询 50 个客户手机号，每个客户返回三类共 8 个信号字段。**数据按"客户单元"汇总**——见下一节定义。

---

## 2. 客户单元的定义（**关键**）

> 这里改变了过去对接时的隐含假设。请仔细对齐。

在本接口中，**一个"客户"= 主账号 + 该主账号名下的所有子账号**，作为一个团队整体看待。返回的所有计数 / 累计 / 是否使用类信号，都是该团队的合计值。

**为什么这样设计：**

- 复盘产品是 B2B 团队工具：注册主账号的通常是团队负责人，实际操作由其下属子账号执行。
- 销售视角下的"客户"是签约的那个团队，不是某个具体登录账号。
- 如果只看主账号的数据，会严重低估实际使用深度（很多老板买了帐号后不亲自操作）；只看子账号则不完整。
- 子账号采用"父子链"建模，深度 ≤2（主账号 → 子账号），不存在嵌套层级歧义。

**聚合规则：**

| 查询入参 phone 命中的账号身份 | 聚合范围 |
|---|---|
| 主账号 | 该主账号 + 其所有子账号 |
| 子账号 | 先回溯到该子账号的主账号，然后按"主账号 + 全部子账号"汇总 |
| 不存在 | 返回 `exists=false`，其余字段零值 |

**举例：**

- 客户 A 的团队有 1 个主账号 + 3 个子账号
- 主账号添加了 2 个直播间账号
- 子账号 1 / 2 各添加了 4 个直播间账号，子账号 3 未添加
- 智能体传入主账号 phone（或任一子账号 phone）查询
- 返回 `addedAnchorCount = 2 + 4 + 4 + 0 = 10`

## 3. 接口约定

### 3.1 基本信息

| 项 | 值 |
|---|---|
| HTTP 方法 | `POST` |
| 路径 | `/internal/crm/customer/behavior-signals` |
| 鉴权 | API Key（沿用现有销售智能体集成接口的同一套 Key 与拦截器） |
| 单次批量上限 | 50 个手机号 |
| Content-Type | `application/json` |
| 超时建议 | 客户端侧建议 1.5s 超时 + 1 次重试 |

### 3.2 请求

```json
{
  "phones": ["13800138001", "13900139002"]
}
```

| 字段 | 类型 | 必填 | 校验 | 含义 |
|---|---|---|---|---|
| `phones` | string\[\] | 是 | size ∈ [1, 50]，每项非空 | 客户手机号列表（去空、去重后处理） |

### 3.3 成功响应

```json
{
  "code": 0,
  "msg": "OK",
  "data": {
    "signals": [
      {
        "phone": "13800138001",
        "exists": true,
        "customerUnitSize": 4,
        "addedAnchorCount": 10,
        "ownAnchorCount": 6,
        "hasUsedOpAssistant": true,
        "hasUsedCompareReplay": false,
        "serviceDurationHours": 720,
        "aiAnalysisTimeConsumed": 14400,
        "totalAiTokensUsed": 850000,
        "recentAiTokensUsed30d": 120000
      },
      {
        "phone": "13900139002",
        "exists": false,
        "customerUnitSize": 0,
        "addedAnchorCount": 0,
        "ownAnchorCount": 0,
        "hasUsedOpAssistant": false,
        "hasUsedCompareReplay": false,
        "serviceDurationHours": 0,
        "aiAnalysisTimeConsumed": 0,
        "totalAiTokensUsed": 0,
        "recentAiTokensUsed30d": 0
      }
    ]
  }
}
```

### 3.4 字段语义

| 字段 | 类型 | 单位 | 语义 | 聚合范围 |
|---|---|---|---|---|
| `phone` | string | — | 回显入参手机号（用于匹配） | — |
| `exists` | boolean | — | 该手机号是否在系统中存在 | — |
| `customerUnitSize` | integer | 个 | 客户团队的账号总数（1 主账号 + N 子账号） | 团队合计 |
| `addedAnchorCount` | integer | 个 | 团队添加的直播间账号总数 | 团队合计 |
| `ownAnchorCount` | integer | 个 | 其中"自有账号"数（非授权他人代管） | 团队合计 |
| `hasUsedOpAssistant` | boolean | — | 团队是否使用过运营助手（历史上有任一次记录即 true） | 团队任一账号 |
| `hasUsedCompareReplay` | boolean | — | 团队是否使用过对比复盘（历史上有任一有效记录即 true） | 团队任一账号 |
| `serviceDurationHours` | integer | 小时 | 客户主账号注册至今的服务时长 | 仅主账号 |
| `aiAnalysisTimeConsumed` | integer | 秒 | 团队累计已消耗的 AI 语音分析时长 | 团队合计 |
| `totalAiTokensUsed` | integer | tokens | 团队历史累计算力消耗 | 团队合计 |
| `recentAiTokensUsed30d` | integer | tokens | 团队近 30 个自然日算力消耗 | 团队合计 |

**`serviceDurationHours` 为何仅按主账号取**：注册时间是团队成立的时间，子账号是后续加入的成员；以主账号注册时间为准更能反映"客户使用产品的总时长"。

### 3.5 错误响应

| 场景 | 返回 |
|---|---|
| API Key 缺失或无效 | HTTP 401 |
| `phones` 为空 | `{ code: 500, msg: "phones不能为空", data: null }` |
| `phones` 数量超过 50 | `{ code: 500, msg: "phones数量不能超过50", data: null }` |
| 子系统部分超时 | HTTP 200，对应字段降级为零值，不级联失败 |

## 4. 字段使用建议（话术切口示例）

> 仅供智能体团队参考，最终话术策略由智能体侧自行决定阈值。

| 信号特征 | 客户画像推断 | 推荐话术方向 |
|---|---|---|
| `addedAnchorCount = 0` | 注册后未启用 | **激活类**：引导首次添加 |
| `0 < addedAnchorCount < 3` ∧ `ownAnchorCount = 0` | 试探使用，全部代管 | **拥有感建立类**：推荐自有账号上手 |
| `addedAnchorCount ≥ 5` ∧ `ownAnchorCount ≥ 3` | 重度自营客户 | **续费 / 增购类**：以使用规模触发扩容 |
| `hasUsedOpAssistant = false` | 未触达核心功能 | **功能 push 类**：约演示 / 试用 |
| `hasUsedOpAssistant = true` ∧ `hasUsedCompareReplay = false` | 单点使用 | **场景延伸类**：从运营助手切到对比复盘 |
| `recentAiTokensUsed30d = 0` ∧ `totalAiTokensUsed > 0` | 已沉睡 | **唤醒类**：以新功能 / 行业案例触达 |
| `recentAiTokensUsed30d > totalAiTokensUsed × 0.5` | 近期重度活跃 | **深度合作类**：高优先级跟进 |
| `customerUnitSize ≥ 5` | 中大团队 | **企业版 / 定制类**：升级套餐 |

阈值（如 ≥5、× 0.5 等）属于智能体侧策略，可后续独立迭代，无需后端配合调整。

## 5. 限制与边界

### 5.1 不返回的字段

接口**不返回**以下信息：

- 子账号明细列表（仅返回 `customerUnitSize` 总数，不列每个子账号身份）
- 任一信号的时间序列（仅返回累计 / 近 30 天 / 是否曾使用，不返回按日趋势）
- 跨租户合并数据（若客户同一手机号在不同团队中使用，仅汇总当前活跃团队）

如需以上数据，需另开评审。

### 5.2 数据延时

- 账号数 / 是否使用类信号：实时
- 算力消耗类信号：分钟级延时（取决于使用记录入库批次）
- 服务时长：实时

### 5.3 数据隐私

- 手机号在调用方与服务端之间传输，但服务端日志中**手机号一律脱敏**（仅记录请求数量，不记录原始号码）
- 接口不返回任何客户的身份证、地址、邮箱等个人敏感信息

## 6. 上线协调步骤

1. **本设计稿评审**（销售智能体团队 + 数据后端团队，目标 1 天内）
   - 字段命名 / 语义 / 聚合范围确认
   - 话术使用建议是否有需要补强的字段
2. **联调环境提供 mock 接口**（评审通过后 1 个工作日内）
   - 智能体团队可针对 mock 完成话术策略前置开发
3. **后端正式实现 + 集成测试**（预计 1 周）
4. **联调通过 → 灰度上线**（按销售智能体灰度名单分批）
5. **正式上线 + 监控埋点**（按使用率 / 异常率分级告警）
