## 一、共同接口规则确认（回复贵稿第二节）

### 1. 成功码 —— 更正：统一 `code=0`

**上一轮回复中"`code=200` 表示成功"是我方笔误，特此更正。** 现有接口与新接口统一约定：

- HTTP 状态码恒为 200，**以响应体 `code` 判断**；
- `code=0` 成功（框架统一判定即 `code == 0`）；
- 通用错误码：`400` 参数错误（不必重试）、`403` api-key 缺失或错误、`500` 服务端异常（只读接口可退避重试）；
- 各接口的业务错误码将在正式文档中逐接口列出完整枚举。

### 2. open-stats 端点数 —— 5 个为准，贵方文档版本偏旧

现行版本 `open-stats-api.md` 共 5 个端点，第 5 个是贵方版本缺少的：

| # | 路径 | 用途 |
|---|---|---|
| 1 | `POST /open/stats/tenant/usage` | 批量租户用量（billedTokens + userMessageCount） |
| 2 | `POST /open/stats/user/usage` | 批量用户用量 |
| 3 | `POST /open/stats/tenant/ai-used` | 批量租户是否使用过 |
| 4 | `POST /open/stats/user/ai-used` | 批量用户是否使用过 |
| 5 | `POST /open/stats/user-tenant/usage` | 批量「用户 × 租户」对用量（入参为 `pairs`，形状与前四个不同） |

请贵方以我方随本回复同步的最新版文档为准。

### 3. 无数据的返回方式

- **现有 open-stats 的行为确认**：请求了几个 id 就返回几条、顺序与入参一致、无数据补 `0/false`、不静默丢 id——即**当前不区分"id 不存在"与"存在但未使用"**。这是现状，如贵方一期需要 open-stats 也区分，属小改造，请明确提出。
- **新接口统一采用三分语义**，`missingReason` 枚举如下（空值=正常有数据）：

| missingReason | 含义 |
|---|---|
| `NOT_FOUND` | 身份或 ID 不存在（含已物理删除） |
| `NOT_MAPPED` | 身份存在但尚未建立租户映射 |
| （无该字段，值为 0/false） | 对象存在、行为确实未发生 |
| `QUERY_FAILED` | 查询失败（该条目失败，不影响批次内其他条目） |
| `NOT_SYNCED` | 数据未同步完成（如存量回填未覆盖） |

权限不足不在条目级表达——整个请求会以 `code=403` 失败。

### 4. ID、时间和枚举

正式文档将固定：所有 ID 字符串返回；时间统一 `yyyy-MM-dd HH:mm:ss`（东八区，与 open-stats 现行为一致；事件推送保留 ISO-8601 带时区格式并在文档标注）；统计一律"左闭右开可传时间窗"，累计值单独命名（`*_total`）不与窗口值混用；所有状态/角色/平台/订单类型/事件类型给出完整枚举表；每条数据带 `observed_at`（实时查询=查询时刻）或 `source_updated_at`（状态类）。

## 二、各项能力正式交付确认（回复贵稿第三节）

### 1. CRM 客户与产品租户映射

- **`crm_customer_id` 的结论**：我方现有接口返回的 userId 就是产品 `user_id`，我方侧**没有独立的 CRM 客户 ID**。若贵方在 CRM 侧另有独立客户 ID，映射入参请传手机号或产品 user_id，出参以 `product_user_id` + `product_tenant_id` 为准，贵方侧自行维护 `crm_customer_id ↔ product_user_id` 对应。
- 接口定义（拟）：`POST /internal/crm/customer/tenant-mapping`，入参 `phones[]` 或 `productUserIds[]`（二选一，≤200）；出参每条：`product_user_id`(str) / `product_tenant_id`(str) / `account_role` / `relation_status` / `source_updated_at` / `missingReason`。
- `relation_status` 枚举：`ACTIVE`（当前有效）/ `INACTIVE_FROZEN`（成员被冻结）/ `INACTIVE_LEFT`（已解绑离开该租户，返回其当前新租户）。
- **映射变化感知**：一期为拉取制——建议贵方按天重拉增量（映射接口支持按 `source_updated_at` 过滤）；变更事件推送列二期。
- 测试环境 / 负责人 / 上线日期：待排期会确认（开发档位：小）。

### 2. 租户成员名单

- **已解绑、已冻结、已删除成员均返回**，靠 `account_status` 区分，不静默丢失：
  - `account_role`：`MAIN`（主账号）/ `SUB`（子账号）；
  - `account_status`：`NORMAL` / `FROZEN`（冻结）/ `LEFT`（已解绑离开租户）/ `DELETED`（已删除）。
- `joined_at`：主账号 = 租户创建时间；子账号 = 绑定时间。`left_at`：解绑时间；从未离开为 `null`（`null` 即"仍在租户"，无其他含义）。
- 批量上限 ≤200 tenant_id。测试环境 / 负责人 / 上线日期：待排期会确认（档位：小–中）。

### 3. 成员登录状态

- **最早可信日期**：登录日志自该表上线起完整；具体日历日期需查生产库后书面补充（本回复暂缺，列为待办）。保留期限：当前无清理任务，即全量保留；若未来引入清理会提前通知。
- **累计与时间窗的字段区分**：`login_count_total`（累计）与 `login_count`（按传入窗口）两个字段并存，同时返回 `start_time/end_time` 回显实际窗口；不传窗口时 `login_count` 不返回。
- 批量接口文档 / 测试环境 / 负责人 / 上线日期：待排期会确认（档位：中）。

### 4. 业务账号（抖音 / 快手 / 视频号）

- `total_count` **= 当前未移除的在册数量**，确认。
- **接受贵方建议：不返回 `active_count`**（我方无独立"有效"概念，不造重复字段）。
- **唯一键确认为 `platform + business_account_id`**。补充一个我方模型事实：同一业务账号可被同租户内多个成员分别添加；汇总按唯一键**去重后**计数，明细按唯一键返回一行，`added_at` 取最早添加时间、`added_by_user_id` 为最早添加人。
- **已移除账号在明细中保留**：`status=REMOVED` + `removed_at`（移除时间）。
- 测试环境 / 负责人 / 上线日期：待排期会确认（档位：小–中）。

### 5. 授权状态（巨量百应 / 千川 / 视频号 / 抖音来客）

- **"从未授权" vs "无记录"**：授权状态是随业务账号落库的本地字段，凡已添加的业务账号必有状态记录，不存在"无法查询"；状态=未授权即"自账号添加以来从未授权成功"。一个已知限制如实说明：状态由客户端操作后回写，若成员长期未使用新版客户端，状态可能滞后于实际——文档中将标注该数据的更新机制。
- **`operator_user_id` = 数据记录所属成员**。授权在该成员自己的客户端内完成，正常情况下所属成员即操作人；若发生代操作（他人登录其账号），我方无法区分，如实说明。
- **授权类型枚举**：`auth_type` ∈ `JLBY`（巨量百应）/ `QIANCHUAN`（千川）/ `WX_CHANNEL`（微信视频号）/ `DOUYIN_LIFE`（抖音来客）。
- **状态枚举**：JLBY / QIANCHUAN / DOUYIN_LIFE 共用：`NONE`(从未授权) / `AUTHORIZED` / `EXPIRED` / `FAILED` / `AUTHORIZING` / `ACCOUNT_MISMATCH`；WX_CHANNEL：`NONE` / `AUTHORIZED` / `REVOKED_BY_PLATFORM` / `REVOKED_BY_USER`。
- **视频号无状态变更时间**：`updated_at` 返回 `null`，数据新鲜度以响应级 `observed_at`（查询时刻，状态为查询时点最新值）表达；**不用其他时间代替**，遵贵方要求。
- **`expires_at` 与授权历史：确认列二期**；一期 `expires_at` 恒为 `null` 并在文档说明。
- 测试环境 / 负责人 / 上线日期：待排期会确认（现状暴露档位：小）。

### 6. 账号分析

- **本期范围：仅直播录像的智能分析**（租户 × 业务账号 × 场次维度）。短视频/达人分析是另一条独立链路，如贵方需要请单独提出，二期评估。
- **三个含义拆为三个字段**，采纳贵方要求：
  - `last_analysis_status`：最近一次分析的状态，枚举 `NONE`(从未发起) / `ANALYZING` / `SUCCEEDED` / `FAILED`；
  - `has_succeeded`：历史上是否成功分析过（布尔，累计口径）；
  - `succeeded_count`：传入时间窗内成功分析次数（回显实际窗口）。
  - 另附 `first_succeeded_at` / `last_succeeded_at`。
- 正式字段表与枚举随接口文档交付。测试环境 / 负责人 / 上线日期：待排期会确认（档位：中）。
