## 2. items[] 区分「不存在/未映射」与「真实零用量」—— 确认改造，方案如下

- **Contract 形状**：5 个端点的 `items[]` 统一增加可空字段 `missingReason`：
  - `null`（不返回该字段）：id 有效，数值为真实统计值——**真实零用量表现为 `missingReason` 缺省 + `0/false`**；
  - `NOT_FOUND`：该 id 在爱复盘用户/租户体系中不存在；
  - `NOT_MAPPED`：id 存在，但其早期数据无法归属租户（仅租户维度端点可能出现，配合 §3.5 口径 3）。
- **实现路径**：智能体服务批量调用爱复盘既有内部接口做存在性校验（用户侧复用现有批量查询，租户侧同型扩展），不引入新数据依赖。
- **兼容性**：新增可空字段，对存量调用方无破坏；随 v1.2 发版。

## 3. 接口 5 增加该用户在该租户下的 `used` —— 确认，随 v1.2 发版

`/open/stats/user-tenant/usage` 的每个 pair 结果增加 `used`（布尔：窗口内该用户在该租户下是否发起过使用），判定口径与端点 3/4 一致（窗口内存在计费结算记录即为 `true`）。底层按 (user, tenant) 对聚合的数据与索引已具备，属小改造。

## 4. 用户多租户语义 —— 定稿：单一激活租户 + 历史可换租户

- 产品模型中，**任一时刻一个用户只有一个激活租户**，其全部使用行为在发生时刻记入当时的激活租户——**不存在"同时多租户并行使用"**。
- 子账号可被绑定/解绑（换租户）。因此**一个用户的历史数据可能分属多个租户**（换绑前后各归各的），这正是接口 5 按「用户 × 租户」对查询的设计动机：跨租户汇总一个用户，请对该用户的多个 pair 分别查询后自行相加。
- 推论：`user/usage`（端点 2）返回的是该用户**跨其全部历史租户**的合计；需要"该用户在某租户下"的口径请一律使用端点 5。此语义将写入正式文档。
