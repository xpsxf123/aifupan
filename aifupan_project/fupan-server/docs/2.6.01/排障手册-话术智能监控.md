## 0. 怎么用这本手册（5 秒判断）

测试发现异常时，先按"现象"分类，再跳到对应章节：

| 现象 | 跳到 |
|---|---|
| 接口直接返非 0 错误码 / 抛 500 | §3 |
| 接口返 0 但 data 异常（字段空 / 类型错 / 数据少了 / 状态卡住） | §4 |

每一节都按"**先查啥 → 怎么解读 → 责任归属（前 / 后 / DBA / 不是 bug）**"三步走。

## 1. 准备：3 张速查表 + 6 条万能 SQL

### 1.1 状态机速查（`tb_script_monitor_report.status`）

| status | 含义 | 用户侧表现 | 期望停留时长 |
|---|---|---|---|
| 0 NOT_GENERATED | 未生成（占位行可能不存在） | 按钮可点 / 显示"生成报告" | — |
| 1 GENERATING | 生成中 | Loading / "AI 生成中" | ≤ 10 min（最坏 ≤ 30 min） |
| 2 GENERATED | 已生成 | 可看报告详情 | 终态 |
| 3 GENERATE_FAILED | 生成失败 | 提示失败 + 可重试 | 终态（手动 trigger 后变 1） |
| 4 NOT_APPLICABLE | 不可生成 | 灰显 + `unavailableReason` | 终态 |

**关键反常组合：**
- `status=1` 但 `update_date < now() - 30min` → 僵尸任务，应被 XXL-Job 推到 3（见 §4.2）
- `status=2` 但 `report_body_id IS NULL` → MongoDB 正文丢失（见 §4.2）
- `status=3` 但 `unavailable_reason IS NULL` → 数据脏，必报后端

### 1.2 监控 / 资源类型速查

| 字段 | 0 | 1 | 2 |
|---|---|---|---|
| `monitor_type` | 质检（QUALITY_INSPECTION） | 还原度（FIDELITY_MONITOR） | 互动巡检（INTERACTION_PATROL） |
| `source_type` | 录制视频（→ `tb_anchor_video.video_id`） | 上传文件（→ `tb_upload_file.file_id`） | — |
| `scene_type` | 复盘 | 视频分析 | 文案预审 |

**本期实现范围（关键，避免误报）**：
- 质检（`monitor_type=0`）：**完整可用**，e2e 跑得通
- 还原度（`monitor_type=1`）/ 巡检（`monitor_type=2`）：**handler 收到 MQ 后返 SUCCESS 但不实际生成**
  - 表现：触发后 `status=1` → 30 min 被僵尸 Job 改成 `status=3`（unavailableReason="系统未响应..."）
  - 这是**已知未实现**，不是 bug；只验状态机正常流转即可

### 1.3 错误码速查（业务码 = `R.code`）

| code | 含义 | 第一步查什么 |
|---|---|---|
| 0 | 成功 | data 字段是否符合契约 |
| 30000 | 数据不存在（通用） | secUid / sourceId / reportId 在不在对应表 |
| 70001 | AI Token 不足 | `tb_user_property` 中 `aiTokenNum`（注意：找**主账号**的） |
| 70002 | 授权数量不足 | `tb_user_property` 中 `scriptQualityNum`（找主账号） |
| 70003 | 套餐不支持 | 当前用户未购买质检包 |
| 70004 | 仅自有账号支持 | `tb_anchor_url_user.account_type` 不是 0 |
| 70005 | 请先确认标准稿 | `tb_anchor_url_user.standard_script_id` = 0 |
| 70006 | 标准稿无效 | `tb_standard_script` 记录被删 / 不在 |
| 70007 | 修改账号类型被锁 | 3 个开关里至少一个 = 1 |
| 70008 | 标准稿生成失败 | 后端 AI 调用失败，重试 |
| 70010 | 本场无弹幕（巡检） | 视频无 barrage 数据 |
| 70011 | 无数据读取权限 | 跨租户 / 非录制人 / 视频归属不对 |
| 70012 | 报告不存在 | reportId 拼错 / 被软删 / 跨租户 |
| 70013 | 参数校验失败 | 看返回 msg 里具体字段 |
| 70014 | 功能未上线 | （注意不是 70005）|
| 70015+ | — | 后端新加，反馈后端 |

**判别 70005 vs 70014 的常见混淆**：70005 是"请先确认标准稿"（已购包，但未配标准稿），70014 是"功能未上线"（整个能力对该租户没开）。看错误码原文不要看猜。

### 1.4 万能 SQL（按"测试拿到的输入"分类）

> 所有 SQL 都基于测试环境 `4395679891245236224` 租户（测试说明书 §1）。换租户改 `tenant_id`。

**SQL-1：按 sourceId（视频 ID / 文件 ID）查所有报告**
```sql
SELECT id AS reportId, monitor_type, status, report_body_id,
       unavailable_reason, trigger_source, create_date, update_date
FROM tb_script_monitor_report
WHERE tenant_id = 4395679891245236224
  AND source_id = '<填 sourceId>'
  AND is_deleted = 0
ORDER BY monitor_type;
```
预期：每个 (sourceId, monitor_type) 最多 1 行（唯一索引 `uk_tenant_source_monitor`）。0 行 → 用户从未触发；3 行 → 三种监控都触发过。

**SQL-2：按 reportId 查全链路（含正文 ID / 已读 / 角色勾选）**
```sql
-- 报告主表
SELECT * FROM tb_script_monitor_report WHERE id = <reportId>;
-- 用户已读
SELECT * FROM tb_script_monitor_read WHERE report_id = <reportId> AND is_deleted = 0;
-- 角色已知晓勾选（质检专用）
SELECT * FROM tb_script_monitor_role_confirm WHERE report_id = <reportId> AND is_deleted = 0;
```
正文要去 MongoDB 查（见 §4.2 步骤 3）。

**SQL-3：查直播间 3 开关 + 标准稿**
```sql
SELECT id, account_type, anchor_url_sec_uid,
       is_script_quality_inspection, is_script_fidelity_monitor, is_interaction_patrol,
       standard_script_id, is_remove_record
FROM tb_anchor_url_user
WHERE tenant_id = 4395679891245236224
  AND user_id = <userId>
  AND anchor_url_sec_uid = '<secUid>'
  AND is_remove_record = 0;
```
注意：软删字段是 **`is_remove_record`**，不是 `is_deleted`（这是 `AnchorUrlUserEntity` 的特例，见 CLAUDE.md §5）。

**SQL-4：查资产（授权数量 / Token 余额）— 必查主账号**
```sql
-- 1. 先确定当前用户是主账号还是子账号
SELECT id, parent_id, account_type, tenant_id FROM tb_user WHERE id = <userId>;
-- parent_id = 0 → 主账号；parent_id != 0 → 子账号，资产看 parent_id 那一行

-- 2. 查资产（注意：本能力 sub_account_have=0，即资产挂主账号）
SELECT upt.user_id, ptt.code, upt.total_quantity, upt.use_quantity,
       (upt.total_quantity - upt.use_quantity) AS remaining_quantity
FROM tb_user_property upt
JOIN tb_user_property_type ptt ON upt.property_type_id = ptt.id
WHERE upt.user_id = <主账号 userId>
  AND ptt.code IN ('aiTokenNum','scriptQualityNum','scriptFidelityNum','interactionPatrolNum');
```
看到 70001 / 70002 必查这里。

**SQL-5：查本地 MQ 消息表（追 MQ 投递 / 消费状态）**
```sql
SELECT id, message_key, message_topic, message_tag, message_status,
       message_body, retry_count, create_date, update_date
FROM tb_mq_message_record
WHERE message_body LIKE '%"reportId":<reportId>%'
ORDER BY create_date DESC LIMIT 5;
```
`message_status`：0=未发送 / 1=已发送 / 2=已消费成功 / 3=发送失败 / 4=消费失败重试中。

**SQL-6：查近 5 分钟僵尸报告**
```sql
SELECT id, tenant_id, source_id, monitor_type, status,
       TIMESTAMPDIFF(MINUTE, update_date, NOW()) AS stuck_minutes
FROM tb_script_monitor_report
WHERE status = 1 AND is_deleted = 0
  AND update_date < NOW() - INTERVAL 30 MINUTE
ORDER BY update_date;
```
本来应该是空。非空 → XXL-Job `scriptMonitorReportZombieRecovery` 没跑 / 跑挂了。

## 2. 关键日志关键字（按 grep 字符串）

测试只看应用日志 `replay-api` + `replay-ai` 两个模块。

| grep 字符串 | 说明 | 在哪类机器 |
|---|---|---|
| `[script-monitor-mq]` | RocketMQ 消费入口日志（收消息 / 拿锁 / 校验幂等） | replay-ai pod |
| `[script-monitor-handler]` | MQ 业务处理（按 tag 路由 / 调 generate） | replay-ai pod |
| `[script-monitor-zombie]` | 僵尸恢复 XXL-Job（每 5 min 跑一次） | replay-ai pod |
| `ScriptMonitorBll` | Controller → Bll 入口（手动 trigger / 状态查询） | replay-api pod |
| `ScriptMonitorGenerateBll` | AI 生成主流程 | replay-ai pod |
| `reportId=<id>` | 全链路追踪（拿 reportId 一定贯穿 4 段日志） | 跨 pod |
| `messageKey=<key>` | MQ 单条消息追踪 | replay-ai pod |

**全链路 grep 套路**（拿到 reportId 后）：
```bash
grep "reportId=<reportId>" replay-api.log replay-ai.log | sort -k1,2
```
正常路径会按时间顺序出现：
1. `ScriptMonitorBll` 写 status=1 + 发 MQ
2. `[script-monitor-mq] 收到消息 ... reportId=...`
3. `[script-monitor-handler] ...`
4. `ScriptMonitorGenerateBll` AI 调用 + 写正文 + status=2

缺哪段就是哪段挂了。

## 3. 现象：接口返非 0 错误码 / 抛 500

### 3.1 业务错误码（code ≠ 0 且 code 是 70xxx / 30000）

**定位流程**：

1. **看 code → 查 §1.3 速查表**，知道含义
2. **看 msg 字段**：后端把具体上下文拼在 msg 里（如 70013 会写"reportId 不能为空"）
3. **按速查表"第一步查什么"跑对应 SQL**
4. 跑完 SQL 还不能解释 → 报后端，提供 `traceId + reportId / sourceId + 入参`

**常见误判**：

| 现象 | 容易误以为 | 实际 |
|---|---|---|
| 70011 "无数据读取权限" | 鉴权挂了 | 跨租户 / 跨用户访问视频；查 SQL-1 看 `tenant_id` 是不是测试账号的 |
| 70002 "授权数量不足" | 套餐没买 | **子账号查不到资产**，需看主账号；走 SQL-4 |
| 70005 "请先确认标准稿" | 系统 bug | 直播间的 `standard_script_id = 0`；走 SQL-3 |
| 70014 "功能未上线" | 同 70005 | 真的没开，找产品 / 联调 toggle |
| 30000 "数据不存在" | 库被删了 | sourceId / secUid 拼错 / 大小写错（**secUid 区分大小写**） |

### 3.2 500 / 异常栈

后端兜底拦截了已知 `BusinessException`，能漏到 500 的基本是：
- NPE（最常见，看栈第一行）
- Feign 调用上游 5xx（看栈里有没有 `feign.FeignException`）
- 数据库连接 / 慢 SQL 超时（栈里有 `SQLException` / `Connection`）

**5 秒判断**：
```bash
grep -A 30 "<traceId>" replay-api.log | grep -E "Exception|Caused by" | head -10
```
有 Caused by → 看最里层那个，复制 4 行栈给后端，**不要只截屏**。

### 3.3 重试相关：`请勿重复提交` / `请勿重复触发`

`triggerReport` 和 `setMonitorEnabled` 都挂了 `@NoRepeatSubmit`：

| 接口 | 防重 key |
|---|---|
| `triggerReport` | `sourceType_sceneType_sourceId_monitorType_token` |
| `setMonitorEnabled` | `secUid_monitorType_enabled_token` |

锁 TTL 由 AOP 默认值决定（一般 ≤ 5 秒）。表现：
- 短时间内（< 5s）连续两次点击 → 第二次会被拒
- 这是**正常防抖**，不是 bug；等 5 秒重试即可
- 如果间隔 ≥ 5 秒还被拒 → Redis 防重 key 残留，找运维清 key（key 前缀看 `replay-common/aspect/lock/repeatsubmit`）

## 4. 现象：接口返 0 但数据不对 / 状态卡住

### 4.1 报告状态卡在 `0` 未生成

**判定**：用户已购包、已开开关、视频也分析完了，但 `reportStatus` 一直返回 status=0。

**步骤**：
1. **是质检吗？** 质检只有"手动 triggerReport"或"B7 自动触发"两条入口。前端不调 trigger，status 永远是 0 → **这是正常**。
2. **是 B7 自动触发场景吗？** 自动触发链路在视频 `analysisStatus=2` 时由 `replay-words` 侧发 MQ → `replay-ai` 创建报告。验证：
   ```sql
   SELECT video_id, analysis_status FROM tb_anchor_video WHERE video_id = '<sourceId>';
   ```
   `analysis_status != 2` → 视频没分析完，不会触发；这是上游的问题，不是质检的。
3. **直播间开关开了吗？** SQL-3 查 `is_script_quality_inspection`；= 0 → 自动触发会跳过。

### 4.2 报告状态卡在 `1` 生成中（**最高频排障场景**）

**判定**：`reportStatus` 返回 status=1，等了很久（≥ 10 min）还没变 2 或 3。

**逐层往下查**（拿到 reportId 后）：

**步骤 1：查报告行本身**
```sql
SELECT id, status, update_date, TIMESTAMPDIFF(MINUTE, update_date, NOW()) AS stuck_min
FROM tb_script_monitor_report WHERE id = <reportId>;
```
- `stuck_min < 10` → 正常，等等
- `stuck_min ≥ 10` 且 `< 30` → 可能 AI 调用慢，继续查日志
- `stuck_min ≥ 30` → 100% 是僵尸，应该被 XXL-Job 推到 3，**Job 没跑**

**步骤 2：查 MQ 是否发出 / 消费**
```sql
-- SQL-5 简化版
SELECT message_status, retry_count, create_date, update_date
FROM tb_mq_message_record
WHERE message_body LIKE '%"reportId":<reportId>%'
ORDER BY create_date DESC LIMIT 1;
```
- 无记录 → trigger 时**写本地消息表挂了**，看 replay-api `ScriptMonitorBll` 日志
- `message_status=0` → 写了表但没发出去；正常情况 XXL-Job 5min 内会接力发；超过 5 min 还是 0 → 接力 Job 挂了
- `message_status=1` 持续 > 5min → broker 收了但 consumer 没消费；查步骤 3
- `message_status=2` → 消费完成，问题在生成阶段；查步骤 4
- `message_status=4` + `retry_count > 0` → 反复消费失败，看 replay-ai 日志

**步骤 3：查 MQ 消费日志**
```bash
grep "messageKey=<key>" replay-ai*.log
```
应该看到 `[script-monitor-mq] 收到消息 ...` → `[script-monitor-handler] ...`：

| 日志关键字 | 解读 |
|---|---|
| `缺少 messageKey` | 上游发消息没带 key（开发问题） |
| `获取锁失败` | 同 messageKey 被并发消费，Redisson 锁拿不到（一般自动重试通过） |
| `未找到消息记录` | broker 投递的 messageKey 不在本地表（脏数据 / DBA 清表过） |
| `消费已发送的消息` 但后续无日志 | handler 调 generate 卡住，看步骤 4 |
| `tag={还原度tag\|巡检tag}` + `未实现，跳过` | **本期未实现**，不是 bug（见 §1.2）|
| `messageKey 重复` | 历史脏数据死信，已被吃掉，正常 |

**步骤 4：查 AI 生成日志**
```bash
grep -E "reportId=<reportId>|ScriptMonitorGenerateBll" replay-ai*.log
```
正常路径会看到：拉视频 / 拉 ASR → 拉提示词 → 调火山引擎 Ark → 解析 → 写 MongoDB → 改 status=2。

| 卡点 | 排查 |
|---|---|
| 拉 ASR 那段日志后无下文 | ASR 拼接慢，看 `tb_anchor_video_asr` 数据量 |
| 调火山 Ark 后超时 / 报错 | 上游 AI 服务问题，复盘 trace |
| 写 MongoDB 失败 | MongoDB 连接 / 集群问题，找运维 |

**步骤 5：兜底 — 僵尸 Job**

如果 status=1 卡 ≥ 30 min 但没自动变 3：
```bash
grep "script-monitor-zombie" replay-ai*.log | tail -20
```
- 应看到每 5 min 一条 `本次扫描共 X 条僵尸，恢复 Y 条`
- 完全无日志 → XXL-Job 调度没起 / handler 没注册；找运维查 XXL-Job 控制台 `scriptMonitorReportZombieRecovery` 任务状态
- 有日志但 `获取锁失败` 持续 → 多实例锁打架，正常情况偶尔出现；连续 5 次以上失败 → Redis 锁泄露

### 4.3 报告状态变 `3` 生成失败

**判定**：`reportStatus` 返回 status=3。

**查 unavailableReason**（SQL-1 或 SQL-2 看 `unavailable_reason` 字段）：

| `unavailable_reason` 字样 | 含义 | 是不是 bug |
|---|---|---|
| `系统未响应（超时 30 分钟）...` | 僵尸 Job 推上来的；说明 generate 实际没跑完 | **是问题**，查 §4.2 步骤 4 |
| `本场无 ASR 数据` | 视频没字幕，无法质检 | 不是 bug，数据本身的问题 |
| `本场无弹幕数据...` | 巡检专用（70010） | 不是 bug |
| `AI 调用失败...` | 火山 Ark 上游报错 | 重试一次；多次失败找后端 |
| `Token 预扣失败...` | 资产侧问题 | 查 SQL-4 是否余额足 |
| 空 / null | 状态脏，必报 | **数据脏数据** |

**复跑路径**：state=3 时再调一次 `triggerReport` 即可，应回到 state=1 → 重走链路。

### 4.4 报告状态显示 `2` 但详情打不开 / 正文空

**判定**：`reportStatus` 返回 status=2，但 `qualityReportDetail` 返回 `reportContent=null` 或字段空。

**步骤**：
1. SQL-2 查报告行 `report_body_id` 字段
   - = null → 状态机不一致，**必须报后端**（generate 中途挂了但状态被写到了 2）
   - 有值（24 位 ObjectId 字符串） → 进步骤 2
2. 去 MongoDB 查正文：
   - 集合：`script_monitor_report_body`（具体名可让后端确认）
   - 查询：`db.script_monitor_report_body.findOne({reportId: NumberLong(<reportId>)})`
   - 查不到 → MongoDB 数据丢，找运维
   - 查到但 `content` 字段为空 → AI 生成时返回空文本，重新触发

### 4.5 列表 / batchReportStatus 少了某些条目

**判定**：传 100 个 sourceId，返回少于 100 条。

**原因**：`batchReportStatus` 设计上**会跳过无权限 / 不存在的资源**（不抛错），少几条是**正常行为**。

**验证**：
1. 拿"少了的 sourceId"单独调 `reportStatus`
2. 看返回错误码：
   - 70011 → 跨租户 / 跨用户，确实无权限，少是对的
   - 30000 → 该 sourceId 真不存在 / 软删，少是对的
   - 返 0 + 正常 data → 批量接口有 bug，报后端

### 4.6 子账号查不到资产 / 显示主账号资产

**判定**：用子账号 token 调 `monitorPositionStatistics`，返回的是主账号的资产，**这是设计如此**（B5 设计：`sub_account_have=0` 即资产挂主账号；子账号能用但看的是主账号余额）。

验证：SQL-4 查子账号 `parent_id`，再用 parent_id 跑一次资产 SQL，应该和接口返的一致。

## 5. 现象：接口慢 / 超时

### 5.1 单接口慢（响应时间 > 1s）

**重点关注接口**：
- `batchReportStatus`（最多 100 条 sourceId）：内部要批量查 4 张表 + Feign 调 2 次
- `qualityReportDetail`：要去 MongoDB 拉正文
- `triggerReport`：要写本地消息表 + 发 MQ + 校验资产 / Token

**步骤**：
1. **看接口响应时间** — Apifox / 浏览器 DevTools Network
2. **查应用日志总耗时**：
   ```bash
   grep "<traceId>" replay-api*.log | grep -E "completed in|耗时|time="
   ```
3. **如果总耗时 - 后端处理时间 > 500ms** → 网络问题，不是后端 bug
4. **后端处理时间 > 1s**：
   - `batchReportStatus` 慢 → 看是不是传了 100 条但很多 sourceId 都跨租户（权限过滤完只剩几条），属正常但可优化
   - `qualityReportDetail` 慢 → MongoDB 慢，找运维
   - 其他接口慢 → DB 慢查询，找 DBA 看 slow log

### 5.2 报告生成慢（status=1 持续 5-10 min）

**正常预期**：
- 质检：3-10 min（看视频时长 / ASR 文本量）
- 短视频（< 30 min 直播）：≤ 3 min
- 长视频（> 2h 直播）：可能 8-10 min

**异常预期**：
- > 10 min 但 < 30 min → 看 §4.2 步骤 4，可能 AI 上游慢
- > 30 min → 走僵尸恢复，应自动变 3

### 5.3 MQ 堆积（多个 status=1 卡住）

```sql
SELECT COUNT(*) AS stuck_count
FROM tb_script_monitor_report
WHERE status = 1 AND update_date < NOW() - INTERVAL 5 MINUTE AND is_deleted = 0;
```
> 10 → consumer 堆积；找运维看 RocketMQ 控制台 consumer group `${rocketmq.script-monitor.consumer-group}` 的堆积量。

## 6. 现象：前后端联调对不上

### 6.1 字段类型不一致

后端约定（看 `API-话术智能监控-接口文档.md`）：

| 字段类型 | 处理 |
|---|---|
| Snowflake ID（`reportId` / `id`）| **string**（防 JS 精度丢失） |
| `tenantId` / `userId` | **string** |
| `monitorType` / `sourceType` / `sceneType` / `status` | **number**（枚举值） |
| 日期（`createDate` / `liveTime`） | **timestamp** 或 `yyyy-MM-dd HH:mm:ss` 字符串，看具体接口 |
| `totalQuantity` / `useQuantity` / `remainingQuantity` | **string** |

**前端报"数字精度丢了"** → 后端 / 前端有一方没按 string 处理，找两边对：
- 后端：看 VO 字段类型是不是 `Long` 没加 `@JsonSerialize`
- 前端：是不是用 `JSON.parse` 把字符串又转成 number 了

### 6.2 响应封装 envelope

所有接口都包 `R<T>`：
```json
{"code": 0, "msg": "success", "data": {...}}
```
- code=0 才是成功，前端必须先判 code
- 不要从 HTTP 200 就推断成功（业务异常 HTTP 也是 200）

### 6.3 契约变更（2.6.01 期内的改动）

**已变更过、前端容易踩的**：

| 接口 | 旧 | 新 | 变更日期 |
|---|---|---|---|
| `reportStatus` | GET + Query | POST + Body | 2026-06-02 |
| `reportStatus` Body | 无 `secUid` | 新增可选 `secUid` | 2026-06-02 |
| `batchReportStatus` SourceItem | 无 `secUid` | 新增可选 `secUid` | 2026-06-02 |
| `triggerReport` | 无 trigger_source 字段 | DB 加 `trigger_source` 字段（接口不变）| 2026-06-03 |

前端报"接口 404 / 405" 第一步先确认 method（GET vs POST）。

### 6.4 字段命名陷阱

| 后端字段 | 实际存储 | 别误以为 |
|---|---|---|
| `summaryJson` | Markdown 文本片段（历史命名遗留，已不是 JSON） | 是 JSON |
| `report.unavailableReason` | 失败原因（任何 status 都可能有） | 只有 status=4 才有 |
| `triggerSource` | 'manual' / 'auto' | bool |
| `confirmRole` | 1=运营 / 2=主播 / 3=主管 | 0 起 |

### 6.5 secUid 大小写

`anchor_url_sec_uid` 在 DB 里是 utf8mb4_0900_ai_ci 排序规则 → **不区分大小写**。但接口校验 / 业务匹配走的是字符串严格匹配 → **区分大小写**。

前端传 `Sec123` vs `sec123` 可能：
- 查 `tb_anchor_url_user` 能命中（DB 不区分）
- 但其他地方按字符串比对会不一致

→ 让前端按用户接口返回的 secUid **原样**传，不要自己改大小写。

## 7. 升级路径（什么时候不该自己继续查）

| 触发条件 | 找谁 | 提供什么 |
|---|---|---|
| 5xx 异常栈含 NPE / Caused by | 后端 | traceId + 完整异常栈 4 层 + 入参 |
| MongoDB 查不到正文 / 集合 | 运维 | reportId + report_body_id |
| MQ 堆积 / 死信 | 运维 | consumer-group + topic + 堆积量截图 |
| XXL-Job 没跑 / 卡 | 运维 | handler name = `scriptMonitorReportZombieRecovery` |
| DB 慢查询 > 5s | DBA | 慢日志原文 + 涉及表 |
| 业务码不在 §1.3 表里 | 后端 | 错误码数字 + 触发场景 |
| 状态机不一致（如 status=2 但 report_body_id=null） | 后端 | reportId + 当前行 dump |
