# 测试指引 — B9 已读语义改造

> **发布日期**：2026-06-08
> **后端版本**：feature/2.6.01 commit `a2553e8e7`
> **覆盖范围**：话术质检 / 话术还原度 / 互动巡检 三类报告的"已读"流程
> **风险等级**：HIGH（破坏性 DDL × 2 + 删 API + 跨 3 模块）
> **上线前置**：执行 `sql/replay-33.sql`（step-by-step 手工）→ 部署新版后端 → 前端同步上线

---

## 1. 本次改了什么（测试视角）

### 1.1 业务流程变化

| 旧流程 | 新流程 |
|---|---|
| 报告生成 → 录制人/运营/主管手动点"确认已读"按钮 → 后端调 `POST /confirmRead` 更新已读状态 | 报告生成 → 录制人打开报告详情接口 → 后端自动写已读，前端无任何动作 |

### 1.2 关键变化点

1. **接口删除**：`POST /replay/script-monitor/confirmRead` 整个下线（HTTP 404）
2. **接口语义变化**：`qualityReportDetail` / `patrolReportDetail` 由"纯读"变为"读 + 副作用写已读"
3. **DDL 破坏性**：
   - `tb_script_monitor_report` 加 2 列：`is_read` / `confirmed_at`
   - 2 张表 DROP：`tb_script_monitor_read` / `tb_script_monitor_role_confirm`
4. **历史数据不 backfill**：上线后所有曾"已读"的报告变回"未读"（前端 UI 会重新出现红点）
5. **重新生成报告时重置**：`triggerReport` 触发后 `is_read=0` / `confirmed_at=null`

## 2. 测试范围

| 范围 | 接口/动作 | 重要度 |
|---|---|---|
| 详情接口写已读 | `GET /qualityReportDetail` / `GET /patrolReportDetail` | P0 |

| confirmRead 已下线 | `POST /confirmRead` | P0 |

| 跨租户访问拒绝 | 跨租户调 detail 接口 | P1 |
| 写已读失败容错 | 模拟 DB 故障 | P2 |

## 3. 测试用例（详细）

### 3.1 录制人首次查看 → 自动写已读（P0）

**前置**：
- 用户 A 是某直播间的录制人（即 `tb_script_monitor_report.user_id = A.id`）
- 报告状态 `status=2`（已生成），`is_read=0`

**步骤**：
1. 用户 A 登录，调 `GET /replay/script-monitor/qualityReportDetail?reportId=<X>`

**预期**：
- HTTP 200
- 响应 `data.isRead === 1`
- 数据库 `tb_script_monitor_report.is_read = 1`、`confirmed_at` 为当前时间
- 列表接口 `batchReportStatus` 中该 reportId 对应 `isRead = 1`

**对应 AC**：AC-001

---

### 3.2 录制人首次查看互动巡检 → confirmedAt 写入（P0）

**前置**：同 3.1，但用 `patrolReportDetail`

**步骤**：
1. 用户 A 调 `GET /replay/script-monitor/patrolReportDetail?reportId=<X>`

**预期**：
- HTTP 200
- 响应 `data.isRead === 1`
- 响应 `data.confirmedAt` 为非 null 时间戳（ISO-8601）
- 数据库 `tb_script_monitor_report.confirmed_at` 写入了当前时间

**对应 AC**：AC-002

---

### 3.3 录制人重复查看 → 幂等（confirmedAt 不变）（P0）

**前置**：3.1 测试后，`is_read=1`，`confirmed_at=T1`（记录此值）

**步骤**：
1. 等待 ≥1 秒
2. 用户 A 再次调 `GET /qualityReportDetail?reportId=<X>`

**预期**：
- HTTP 200，`isRead === 1`
- 数据库 `confirmed_at` **仍为 T1**（不被覆盖为新时间）
- 无异常日志

**对应 AC**：AC-004

---

### 3.4 同租户非录制人查看 → 不写已读（P0）

**前置**：
- 用户 B 与 A 同租户，但 B 不是录制人
- 报告 `is_read=0`

**步骤**：
1. 用户 B 调 `GET /qualityReportDetail?reportId=<X>`

**预期**：
- HTTP 200，能看到报告详情
- 响应 `data.isRead === 0`（保持未读）
- 数据库 `tb_script_monitor_report.is_read` 仍为 0
- 数据库 `confirmed_at` 仍为 null

**对应 AC**：AC-005

---

### 3.5 跨租户访问 → 拒绝（P1）

**前置**：用户 C 与报告所在租户不同（`user.activeTenantId ≠ report.tenantId`）

**步骤**：
1. 用户 C 调 `GET /qualityReportDetail?reportId=<X>`（或 `patrolReportDetail`）

**预期**：
- HTTP 200 但响应 `code` 为错误码 70011（`SCRIPT_MONITOR_NO_PERMISSION`），`msg` 含"无数据读取权限"
- 数据库 `is_read` 不变

**对应 AC**：AC-006

---

### 3.6 报告不存在 / 已软删 → NOT_EXIST（P1）

**前置**：传入一个不存在的 `reportId`，或一个 `is_deleted=1` 的 reportId

**步骤**：
1. 用户 A 调 `GET /qualityReportDetail?reportId=<不存在 ID>`

**预期**：
- 响应错误码 70006（`SCRIPT_MONITOR_REPORT_NOT_EXIST`）

**对应 AC**：AC-007

---

### 3.7 confirmRead 接口已删除（P0）

**前置**：任意已登录用户

**步骤**：
1. 调 `POST /replay/script-monitor/confirmRead`（带任意 body）

**预期**：
- **HTTP 404**（路径不存在）

**对应 AC**：AC-008

---

### 3.8 列表 isRead 来源主表（P0）

**前置**：
- 数据库直接 `UPDATE tb_script_monitor_report SET is_read=1 WHERE id=<X>`
- 不通过任何接口操作

**步骤**：
1. 调 `POST /batchReportStatus`（含该 reportId 对应的 source）

**预期**：
- `monitors[质检].isRead === 1`
- 不调任何子表（`tb_script_monitor_read` 已删，调了会 SQL 错）

**对应 AC**：AC-003 / AC-009

---

### 3.9 响应字段下线检查（P0）

**步骤**：
1. 调 `qualityReportDetail` → 响应 JSON
2. 调 `patrolReportDetail` → 响应 JSON
3. 调 `batchReportStatus` → 响应 JSON

**预期**（每个响应都满足）：
- **没有** `confirmedRecords` 字段（旧三角色勾选列表）
- **没有** `canConfirm` 字段
- 有 `isRead` 字段（值 0/1）
- `patrolReportDetail` 多出 `isRead` + 有 `confirmedAt` 字段

**对应 AC**：AC-010

---

### 3.10 triggerReport 重新生成 → 重置 is_read / confirmed_at（P1）

**前置**：报告 `is_read=1`、`confirmed_at` 非 null（先跑 3.1 后到此态）

**步骤**：
1. 用户 A 调 `POST /triggerReport`（手动触发已生成报告的重新生成）

**预期**：
- 数据库 `is_read` 被重置为 0
- 数据库 `confirmed_at` 被重置为 NULL
- 接口正常返回

**对应 AC**：AC-013

---

### 3.11 写已读失败 → 不影响详情返回（fail-safe）（P2）

**前置**：模拟 `tb_script_monitor_report` 写不进（如 DB 短暂只读）

**步骤**：
1. 用户 A（录制人）调 `qualityReportDetail`

**预期**：
- HTTP 200，详情正常返回
- 响应 `isRead === 0`（因为写失败，返回 stale 值）
- 后端日志含 `[B9] markReadIfNeeded 写已读失败 reportId=<X>` WARN

**测试方式**：开发人员配合在 `markReadIfNeeded` 内临时抛 RuntimeException 复现，正式测试环境难复现可跳过

**对应 AC**：AC-012

---

### 3.12 DDL 幂等性（P1）

**前置**：`sql/replay-33.sql` 已在测试环境执行一次

**步骤**：
1. 再次手工执行同一份 SQL（逐条 step）

**预期**：
- 无报错（`ADD COLUMN IF NOT EXISTS` + `DROP TABLE IF EXISTS` 守护）
- 数据库结构无变化

**对应 AC**：AC-011

## 4. 历史数据回归（重要！）

### 4.1 升级前确认

- 记录上线前 `tb_script_monitor_read` 中 `is_read=1` 的记录数（这些是历史已读）
- 抽样几条已读报告，记下 `reportId`

### 4.2 升级后验证

- DDL 执行后：`tb_script_monitor_report.is_read` 全部为 0（默认值，未 backfill）
- 上面抽样的报告，前端列表都应显示"未读"（红点恢复）—— **这是符合预期的行为**，产品侧已知悉
- 让录制人本人打开任意一份历史报告 → `is_read` 立即变 1，列表红点消失

### 4.3 异常报告

如果发现：
- 录制人打开报告 → `is_read` 仍为 0（写已读失败）
- 后端日志没 `[B9] markReadIfNeeded` 字样 → 后端调用链异常
- DROP TABLE 后还有 SQL 试图查老表 → 后端代码漏改

→ 立即反馈给后端 beta。

## 5. 性能 / 监控关注点

- `markReadIfNeeded` UPDATE 走主键点查 + tenantId 过滤，P99 < 5ms 应保证
- `batchReportStatus` 性能应略改善（少一次 IN 查询）
- 后端日志关键字：`[B9] markReadIfNeeded`（写已读失败时会出现）

## 7. 回归范围

除了本次新增/变更的接口，回归以下与"已读"无关但走同一 Controller 的接口，确认没被误伤：

- `POST /triggerReport`（除了 3.10 的重置语义）
- `POST /reportStatus`（单资源状态查询）
- 报告生成定时任务 / MQ 链路（自动触发场景）

## 8. 上线流程协同（运维）

1. 执行 `sql/replay-33.sql`（**step-by-step 手工** 一条一条执行，任一 step 失败立即停止；不可批量复制粘贴）
2. 部署新版后端
3. 通知前端同步上线
4. 测试团队按本文档 P0/P1 跑一遍
5. 监控后端日志一小时内有无 `[B9] markReadIfNeeded` WARN 异常累计

**回滚预案**：DDL 不可回滚（DROP TABLE 后旧代码无法运行）。如必须回滚，需 DBA 重建两张子表 + 后端回滚到 `cc40e159e` 之前的版本（replay-32）。回滚成本高，**优先排查不要回滚**。
