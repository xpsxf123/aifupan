## 1. 系统全局说明

### 1.1 系统业务背景
本系统为面向直播电商企业（包括单一企业、多品牌集团、MCN机构、代运营公司）的 SaaS 管理后台。解决的核心痛点是：**直播排班的复杂性**（跨天、多班次、多角色频繁变动）以及**业绩核算的精细化**（如何将一场直播的总业绩，科学、合理、自动地分摊给参与该场直播的不同时间段、不同岗位的人员）。

### 1.2 全局通用业务规则
1. **多租户数据绝对隔离**：各企业（租户）数据完全独立。所有业务表的查询、写入默认带入/校验 `tenant_id`。
2. **逻辑删除防呆机制**：系统内所有核心资产（人员、排班、直播间等）均采用逻辑删除（`is_deleted`）。删除时需强制校验关联资产。
3. **审计追溯**：核心表必须记录 `create_by` (创建人) 和 `update_by` (修改人)，以便出现业绩纠纷时进行操作审计。

## 2. 权限与账号模块

本模块解决“谁能登录系统，登录后能看到哪些菜单，能操作哪些数据”的问题。

### 2.1 核心功能：角色与权限分配

#### 2.1.1 业务流程：新增角色与赋权
1. **企业管理员**进入“角色管理”列表。
2. 点击“新增角色”，填写角色名称（如“高级场控”）。
3. **选择数据权限范围**（单选）：1-仅看个人，2-看本小组，3-看本部门，4-看本公司，5-看全公司。
4. **勾选功能权限**：展示树状菜单（菜单-页面-按钮），支持父子节点级联勾选。
5. 保存后，在“人员管理”中将该角色分配给指定员工。

#### 2.1.2 深度业务规则与边界约束
*   **同名拦截**：角色名称在当前租户下必须唯一（排除已删除的数据）。
*   **角色安全删除**：当角色被分配给任意未删除状态的员工时，**绝对禁止删除**该角色。系统需强提示：“该角色下存在N名员工，请先解除关联”。
*   **超级管理员兜底**：每个租户初始化时，系统内置一个“租户管理员”角色（不可编辑、不可删除、拥有最高权限），该角色拥有所有界面的访问权及“看全公司”的数据权限。
*   **权限并集规则**：一个员工可配置多个角色。
    *   **功能权限**：取所有角色勾选的**并集**。
    *   **数据权限**：取所有角色中**最大的范围**（例如：同时拥有“看本部门”和“看全公司”角色，最终生效为“看全公司”）。
*   **菜单自动隐现**：如果用户没有任何某主菜单下属的子页面或按钮权限，该主菜单在左侧导航栏必须自动隐藏。

## 3. 组织架构与人员模块

构建企业的“公司-部门-小组”三级树状结构，并管理员工全生命周期。

### 3.1 核心功能：组织架构管理

#### 3.1.1 业务操作步骤
*   **子公司管理**：支持新增、修改名称。所有下级组织必须挂载在子公司下。
*   **部门管理**：新建部门时，必须选择上级子公司。
*   **小组管理**：新建小组时，必须选择上级部门。

#### 3.1.2 深度业务规则与边界
*   **层级名称防重**：同一层级下的组织名称不能重复（如：A公司下不能有两个叫“直播一部”的部门）。
*   **安全删除规则 (级联阻断)**：
    *   删除子公司前：若其下存在未删除的部门、员工或直播间，**禁止删除**。
    *   删除部门前：若其下存在未删除的小组、员工或直播间，**禁止删除**。
    *   删除小组前：若其下存在未删除的员工或直播间，**禁止删除**。
*   **部门负责人委派**：允许将某位员工设置为部门或小组的“管理员”。该身份将用于未来排班审批流及专属数据看板的默认权限判定。

### 3.2 核心功能：员工全生命周期管理

#### 3.2.1 业务流程：员工入职与调岗离职
1. **新增员工**：HR或管理员手动新增或批量导入员工，填写手机号、姓名。
2. **分配归属与角色**：选择员工所属的 公司/部门/小组，选择系统岗位（主播、场控等）及系统角色。
3. **日常管理 (调岗)**：修改员工的组织归属或岗位，权限和数据归属实时变更。
4. **离职处理**：停用账号。

#### 3.2.2 深度业务规则与边界 (重点)
*   **唯一性凭证**：手机号 (`mobile`) 是租户内员工的唯一登录凭证，绝对不可重复。
*   **员工离职/删除核心规则 (强管控)**：
    1.  **历史资产保护**：操作员工离职时，仅改变 `account_status` (设为停用) 或 `is_deleted` (设为1)。其过去产生的所有**业绩数据和历史排班记录必须永久保留**，不能做任何物理清除，以供财务对账。
    2.  **未来排班阻断**：操作离职/删除时，系统必须自动检测该员工在**今天及未来日期**是否还有未执行的排班。如果有，必须阻断离职操作，弹窗提示：“该员工未来还有 N 个排班未处理，请先进行调班或取消排班”。
*   **组织调动与业绩切割**：当员工从 A部门 调动到 B部门 时，自操作调动生效之日起，该员工新产生的业绩归属 B部门；其调动之前产生的历史业绩，**依然永久归属于 A部门**（在报表统计时，需基于每天的快照数据进行上卷聚合，不能直接取最新部门关联）。

## 4. 直播间管理模块

直播间是“场”的载体，是连接主播和产生业绩的源头。

### 4.1 核心功能：直播间创建与配置

#### 4.1.1 详细操作步骤
1. 点击“新增直播间”，选择平台（抖音/快手/视频号）。
2. 输入主播的平台唯一标识 (`sec_uid`)。
3. 系统调用平台开放API，自动拉取并回填主播昵称、头像。
4. 将直播间绑定到指定的 公司/部门/小组 组织架构上。
5. 配置该直播间的“排班规则”（营业时间、允许的班次时长、允许的岗位）。

#### 4.1.2 深度业务规则与边界
*   **跨租户防盗刷安全规则**：同一个 `sec_uid`（同一个抖音号）在**全系统（跨租户）层面**原则上只允许被一个有效租户绑定。若强行绑定，需触发平台授权认证流程，防止 A公司 恶意拉取 B公司 主播的数据。
*   **直播间业绩归属**：直播间产生的场次原始业绩，向上汇总给其绑定的组织架构。
*   **排班强管控引擎 (`live_room_schedule_attribute`)**：
    *   **营业时间约束**：如配置 `start_plan=08:00`, `end_plan=24:00`，则该直播间不允许任何人排 02:00 的班。
    *   **岗位约束**：如仅允许“主播”和“副播”排班，则尝试给“场控”排该直播间的班时会被直接拦截。

## 5. 排班调度模块 (核心)

本系统最复杂的业务流之一。直播行业排班无固定双休，经常面临 24小时连播、跨天排班及频繁换班。

### 5.1 核心功能：排班创建与防错检测

#### 5.1.1 详细操作步骤
1. **排班员**进入日历视图或列表视图，选择目标日期和直播间。
2. 选择岗位，选择需要上播的员工。
3. 设定精确的上播时间 (`start_work`) 和 下播时间 (`end_work`)。
4. 点击保存，系统触发**“排班防错引擎”**检测。
5. 检测通过后落库，生成排班记录，状态为“待执行”。

#### 5.1.2 排班防错引擎规则 (极其重要)
*   **硬阻断 1：单人时间重叠**
    同一个员工，在相同的绝对时间段内，绝对不允许存在两条有效排班记录。
    *(特例：不同的员工可以在同一直播间的同一时间段排班，例如双主播同台)*
*   **硬阻断 2：跨天时间逻辑**
    系统在比较时间重叠时，必须将时间转换为绝对时间戳或 `MMDDHHmm` 整数进行比较。例如：归属日为 3月1日 的排班，时间从 22:00 到次日 02:00。当为该员工排 3月2日 01:00 的班次时，必须能识别出冲突并拦截。
*   **硬阻断 3：越界配置**
    排班的起止时间、所选岗位必须完全符合该直播间预设的规则。
*   **软提示 1：疲劳度与工时预警**
    当检测到该员工单日累计排班总时长超过 8 小时，或连续两次排班的休息间隔不足 6 小时，系统允许保存，但必须弹出**标红的警告确认框**提示操作人。

### 5.2 核心功能：调班与取消

#### 5.2.1 业务规则
*   **状态限制**：只有状态为“待执行”或“进行中”的排班允许调班或取消。“已完成”的排班原则上禁止直接修改。
*   **调班逻辑**：调班等同于“原排班逻辑删除” + “生成一条新员工的新排班记录”，并记录操作日志以备查。
*   **联动核算（关键）**：如果因为特殊情况，管理员修改了**过去几天**的排班记录，系统必须**自动触发**这段时间相关直播间场次业绩的**重新核算与分摊**任务。

## 6. 场次与视频流模块

负责从巨量引擎/千川等平台获取客观的直播销售结果数据。

### 6.1 核心功能：数据采集与清洗

#### 6.1.1 自动拉取与补录流
1. **自动同步**：系统后台每隔 5-10 分钟自动调用平台 API，拉取最新的场次数据 (`live_session`)，包含：总场观 (`view_count`)、累计销售额 (`end_sales`)、退款额 (`refund`)、广告消耗 (`investment`)。
2. **断播重连处理**：一场预定直播中途断网重开，平台会生成两个独立的 `session_id`。系统无需合并，直接作为两场独立场次进行后续排班的业绩分摊。
3. **手动补录**：若 API 接口故障，系统允许超级管理员手动录入场次数据 (`source=2`)。手动录入行为必须留存审计日志。

#### 6.1.2 退款滞后性处理规则 (T+N 回溯)
*   直播电商的退款通常发生在直播结束后的数天内。
*   **规则**：系统每天凌晨触发定时任务，回溯拉取过去 7 天内所有场次的最新退款数据，更新 `refund` 字段。
*   **衍生计算**：更新后，系统自动重算净销售额 (`net_sales = end_sales - refund`) 和 ROI (`net_sales / investment`)。*注意：ROI 计算代码必须前置校验 `investment > 0` 以防除零异常*。

## 7. 业绩核算与分摊模块 (核心算法)

本系统的**最高业务价值所在**。解决如何将粗颗粒度的“场次数据”精准分摊给细颗粒度的“排班人员”。

### 7.1 核心算法：基于时间重叠比例的切割法

#### 7.1.1 业务场景举例
*   **客观场次数据**：某直播间实际开播 10:00 - 14:00 (共4小时)，总净销售额 40000元。
*   **系统排班数据**：
    *   主播A：10:00 - 12:00 (在岗2小时)
    *   主播B：12:00 - 14:00 (在岗2小时)
    *   场控C：10:00 - 14:00 (在岗4小时)

#### 7.1.2 详细计算步骤与落库
1.  **触发时机**：当场次数据结束/更新时，或关联的排班数据发生变动时触发。
2.  **寻找交集**：系统查询出与该场次绝对时间段（10:00-14:00）有交集的所有排班记录。
3.  **计算个人重叠时长**：A重叠2小时，B重叠2小时，C重叠4小时。
4.  **计算分摊比例**：比例 = 个人重叠时长 / 场次总时长。
    *   A的比例 = 2/4 = 50%
    *   B的比例 = 2/4 = 50%
    *   C的比例 = 4/4 = 100%
5.  **指标切分**：
    *   A的个人业绩 = 40000 * 50% = 20000元
    *   B的个人业绩 = 40000 * 50% = 20000元
    *   C的个人业绩 = 40000 * 100% = 40000元
    *(注：各岗位平行核算，不相互稀释。主播A和B瓜分了该场次的销售额，而场控C独自拿到了全额)*
6.  **落库**：将每一条计算结果存入 `schedule_session` (排班场次业绩明细表)，随后按日汇总写入 `staff_performance` (人员日业绩汇总表)。

#### 7.1.3 核心边界与异常处理
*   **浮点数精度损耗**：在按比例切分时必然产生除不尽的小数。系统规定：中间计算过程保留 4 位小数，最终落库存款金额时采用 `ROUND_HALF_UP` 保留 2 位小数。允许分摊相加的总额与场次总额存在极微小的几分钱误差。
*   **跨天场次切割**：若一场直播从 23:00 播到次日 02:00。业绩将严格按重叠时间比例，切分到 23:00-24:00 的排班记录（计入昨日业绩）和 00:00-02:00 的排班记录（计入今日业绩）中。
*   **无主业绩预警**：如果拉取到场次数据，但在对应时间段内找不到任何排班记录，该场次业绩将变为“无主数据”。系统需在首页产生“异常告警”，提醒管理员前去“补排班”，补完后点击“一键重算”。

### 7.2 每日统计宽表引擎 (`daily_stats`)
*   为了支撑前端报表大屏的极速加载，不建议每次实时 Join 表。
*   **定时快照**：每天凌晨 02:00，系统执行离线任务，将前一天的所有数据聚合，写入 `daily_stats` 宽表。
*   **层级上卷**：根据排班当时的组织架构关系，向上逐级累加 场观、销售额、投放消耗 等数据。当表中的 `dept_id` 或 `team_id` 为 0 时，代表该条记录为该层级的汇总汇总数据。

## 8. 商品分析模块

用于分析具体某款商品在直播中的漏斗转化表现。

### 8.1 核心业务规则
*   **商品数据挂载**：系统从平台拉取的商品表现（销量、退单量、曝光量），必须强关联到具体的场次 ID 上，落库至 `session_product` 表。
*   **核心指标定义**：
    *   `gpm` (千次观看成交额/GPM) = `(sales_amount / 场次总 view_count) * 1000`。
    *   `click_payment_rate` (点击付款转化率) = 付款单量 / 点击次数。
*   **退款率滚动更新**：和场次级别一样，单款商品的退单量具有滞后性。夜间定时任务需同步更新商品维度的 `refund_quantity` 和 `refund_rate`。

## 9. 附录：全局数据字典

| 领域 | 字段 | 枚举值 | 业务含义 |
|---|---|---|---|
| 全局 | is_deleted | 0, 1 | 0-正常, 1-逻辑删除。所有唯一约束必须联合此字段。 |
| 人员 | job_type | 1, 2 | 1-全职, 2-兼职。兼职人员在排班时可能免除某些工时预警。 |
| 人员 | account_status| 0, 1 | 0-停用, 1-正常。停用后不可登录系统，但历史业绩保留。 |
| 直播间 | platform | 0, 1, 2 | 0-抖音, 1-快手, 2-视频号。决定了调用哪套开放平台API。 |
| 数据流 | source | 1, 2 | 1-系统自动拉取/自动计算, 2-人工手动录入/干预。 |
